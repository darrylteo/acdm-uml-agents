# The document: sixteen A-CDM milestones, sentences numbered

## Milestone 1: ATC Flight Plan Activated

### Definition

[M1.definition.1] The ICAO flight plan is submitted to ATC.
[M1.definition.2] The Airport CDM Platform is initiated for this flight, and all available information is processed.
### Origin and priority

[M1.origin_and_priority.1] The ATC Flight Plan is submitted by the Aircraft Operator and distributed by the IFPS.
[M1.origin_and_priority.2] All involved ATC units receive the flight plan, including departure and destination aerodromes.
### Timing

[M1.timing.1] Normally this takes place 3 hours before EOBT, however it may be later.
[M1.timing.2] In some cases a repetitive flight plan (RFPL) has been submitted, covering daily or weekly flights.
### Data Quality

[M1.data_quality.1] The ATC Flight Plan corresponds to the airport slot programme.
### Effect

[M1.effect.1] One aircraft turn-round normally includes an arriving and a departing flight, meaning that it will have two related flight plans.
[M1.effect.2] For coordinated airports, the outbound flight is already known.
[M1.effect.3] The flight plan may be used to update certain information such as type of aircraft.
[M1.effect.4] For long distance flights, the ELDT may differ from the airport slot.
[M1.effect.5] For non coordinated airports, the flight plan is used to initiate the outbound flight.
[M1.effect.6] The flight is ready not later than 15 minutes after the planned EOBT.
[M1.effect.7] The DPI process commences the correct messaging with Network Operations (if implemented - see attachment 2 for details).
### Procedures

[M1.procedures.1] To check consistency between ATC Flight Plan, Airport Slot and Airport flight data and then confirm the flight to the Network Operations and allow further local processing of the flight.
[M1.procedures.2] This check shall be performed to verify the consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
[M1.procedures.3] The AO must provide correct information before this first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible.
[M1.procedures.4] The E-DPI message should not be sent if no or inconsistent information is provided.
[M1.procedures.5] This process is triggered by:
[M1.procedures.6] - The first activation of the ATC Flight Plan (earliest EOBT-3 hr), or
[M1.procedures.7] - New or late submissions of the ATC Flight Plan, after cancellation or revised EOBT
### Operational Status (changes to)

[M1.operational_status.1] INITIATED
### Action on CDM Operation (ACISP)

[M1.action_on_cdm.1] ELDT and EIBT updated for an arrival EOBT and ETOT updated for a departure The DPI process commences (if implemented - see section 3.7.3 for details).
## Milestone 2: EOBT - 2 hr

### Definition

[M2.definition.1] At EOBT-2 hr most flights will be known in the Airport CDM Platform including if they are regulated or not.
[M2.definition.2] All regulated flights receive a CTOT from Network Operations.
### Origin and priority

[M2.origin_and_priority.1] The CTOT is issued by the Network Operations and is sent to relevant ATS units as well as the departure aerodrome.
[M2.origin_and_priority.2] CTOT flights usually have a priority over unregulated flights.
### Timing

[M2.timing.1] If the flight is regulated, a CTOT is issued at EOBT-2h.
### Data Quality

[M2.data_quality.1] Not applicable.
### Effect

[M2.effect.1] For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.
### Procedures

[M2.procedures.1] To check (before or after take off from outstation) whether AO/GH flight estimates are consistent with the ATC Flight Plan and to inform Network Operations about the updated take off time estimate, using a T-DPI Message.
[M2.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs.
[M2.procedures.3] At EOBT-2 hrs Network Operations is informed through the first T-DPI message.
[M2.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT.
[M2.procedures.5] In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M2.procedures.6] This procedure is triggered by
[M2.procedures.7] - a time stamp, at EOBT - 2h.
### Operational Status (changes to)

[M2.operational_status.1] N. A.
### Action on CDM Operation (ACISP)

[M2.action_on_cdm.1] ETOT/TTOT/CTOT Mark appropriate fields as REGULATED
## Milestone 3: Take Off from Outstation

### Definition

[M3.definition.1] The ATOT from the outstation (ADEP)
### Origin and priority

[M3.origin_and_priority.1] The outstation provides ATOT to the Network Operations and Aircraft Operator.
### Timing

[M3.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M3.data_quality.1] The accuracy of ATOT is +/- 1 minute.
### Effect

[M3.effect.1] If the departure airport is more than 3hrs flying time from the destination airport the ATOT is received from either the Network Operations FUM or via the Aircraft Operator / Ground Handler.
[M3.effect.2] Using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
[M3.effect.3] If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS and send a Flight Update Message (FUM) that provides updates of the flight's progress.
### Procedures

[M3.procedures.1] To check whether the AO/GH estimated landing time after take off from outstation are consistent with the outbound ATC Flight Plan, and when needed inform the Network Operations about the updated take off time estimates using a T-DPI-t Message.
[M3.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation.
[M3.procedures.3] A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT.
[M3.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT.
[M3.procedures.5] In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT.
[M3.procedures.6] In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M3.procedures.7] This process is triggered by
[M3.procedures.8] - the take off from outstation.
### Operational Status (changes to)

[M3.operational_status.1] AIRBORNE
### Action on CDM Operation (ACISP)

[M3.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 4: Local Radar Update

### Definition

[M4.definition.1] The flight enters the FIR (Flight Information Region) or the local airspace of the destination airport.
### Origin and priority

[M4.origin_and_priority.1] This information is normally available from the Area Control Centre (ACC) or Approach Control Unit that is associated with an airport.
[M4.origin_and_priority.2] The radar system is able to detect a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
### Timing

[M4.timing.1] Dependent upon the position of the airport in relation to the FIR boundary.
### Data Quality

[M4.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M4.effect.1] Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.
[M4.effect.2] The accuracy of ELDT is particularly important at this stage since downstream decisions are taken, such as stand /gate / aircraft changes, preparation of arrival sequence, preparation of ground handling operations, decisions for connecting passengers.
[M4.effect.3] Uncertainty and ELDT non-accuracy at this stage significantly increase risks for bad and last minute decisions and internal disruptions.
[M4.effect.4] The objective to decrease the number of stand and gate changes in the last 30 minutes requires high accuracy regarding departure and arrival times.
[M4.effect.5] Therefore, taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.
[M4.effect.6] The update of TOBT for the related departing flight takes place following this milestone.
[M4.effect.7] Decisions such as the turn-round period, connecting passengers etc are taken and need to be stable at this event.
[M4.effect.8] An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
### Procedures

[M4.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M4.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M4.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M4.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M4.procedures.5] This process is triggered by
[M4.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M4.operational_status.1] FIR
### Action on CDM Operation (ACISP)

[M4.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 5: Final Approach

### Definition

[M5.definition.1] The flight enters the Final Approach phase at the destination airport.
### Origin and priority

[M5.origin_and_priority.1] This information is normally available from ATC.
[M5.origin_and_priority.2] The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range / position or passes/leaves a predetermined level.
### Timing

[M5.timing.1] Dependent upon local parameters that are defined by ATC.
### Data Quality

[M5.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M5.effect.1] Update of the ELDT to determine a new TOBT.
[M5.effect.2] When a flight reaches this stage it is usually between 2 and 5 minutes from landing (depending on the parameter set by ATC).
[M5.effect.3] This is often the prompt for many partners to start moving resources connected with the flight, such as positioning a parking marshal and ground handling services.
### Procedures

[M5.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M5.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M5.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M5.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M5.procedures.5] This process is triggered by
[M5.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M5.operational_status.1] FINAL
### Action on CDM Operation (ACISP)

[M5.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 6: Landed

### Definition

[M6.definition.1] ALDT - Actual Landing Time.
[M6.definition.2] This is the time that an aircraft touches down on a runway.
[M6.definition.3] (Equivalent to ATC ATA - Actual Time of Arrival landing, ACARS=ON).
### Origin and priority

[M6.origin_and_priority.1] Provided by ATC system or by ACARS from equipped aircraft.
### Timing

[M6.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M6.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M6.effect.1] The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator / Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
[M6.effect.2] The EIBT can be updated according to the ALDT +EXIT.
### Procedures

[M6.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M6.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M6.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
[M6.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M6.procedures.5] This process is triggered by
[M6.procedures.6] - Actual Landing Time: ALDT
### Operational Status (changes to)

[M6.operational_status.1] LANDED
### Action on CDM Operation (ACISP)

[M6.action_on_cdm.1] ELDT changes to ALDT, EIBT, TOBT and TTOT updated

## Milestone 9: Final Confirmation of the TOBT

### Definition

[M9.definition.1] The time at which the Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.
### Origin and priority

[M9.origin_and_priority.1] The Aircraft Operator / Ground Handler provides the information.
### Timing

[M9.timing.1] The information is provided t minutes before EOBT (t is a parameter time agreed locally).
### Data Quality

[M9.data_quality.1] Accuracy is agreed locally.
### Effect

[M9.effect.1] The aim of the final TOBT is to give a timely, accurate and reliable assessment of the off-block time.
[M9.effect.2] It is recognised that main benefits of sharing the TOBT are expected in case of disruptions (internal or external).
[M9.effect.3] In such cases, the difference between EOBT (shared by ATC, Network Operations and Stand / Gate Management) and TOBT may be important.
[M9.effect.4] An accurate TOBT at [EOBT-t minutes] is a pre-requisite for ATC to establish a push back / pre-departure sequence.
[M9.effect.5] Emphasis is put on the need for the Aircraft Operator to integrate his own strategy to compute a TOBT related to the flight.
[M9.effect.6] Following the receipt of the TOBT, the ATC system will calculate and provide the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate / stand location, runway in use, and waiting period at the Holding Position, etc. The flight is introduced into the pre-departure sequence.
[M9.effect.7] The Aircraft Operator / Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M9.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M9.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M9.procedures.3] This check should be performed at a predefined time (local parameter) to confirm TOBT prior to TSAT issue and verify feasibility of the ATC Flight Plan estimates given the updated TOBT.
[M9.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M9.procedures.5] This Milestone Process is actually constantly applicable in the CDM Platform, as soon as a TOBT is available.
[M9.procedures.6] However the confirmed TOBT prior to TSAT has special status, where AO/GH check the quality of TOBT before TSAT issue.
### Operational Status (changes to)

[M9.operational_status.1] IN-BLOCK
### Action on CDM Operation (ACISP)

[M9.action_on_cdm.1] This process is triggered by - a new TOBT or TTOT update.
[M9.action_on_cdm.2] No need to confirm an existing TOBT if it has been manually modified before.

### Definition

[M10.definition.1] The time ATC issues the Target Start Up Approval Time
### Origin and priority

[M10.origin_and_priority.1] ATC
### Timing

[M10.timing.1] The information is provided t-minutes before EOBT, where t is a parameter agreed locally
### Data Quality

[M10.data_quality.1] Accuracy is agreed locally.
### Effect

[M10.effect.1] The flight is stabilised into the pre-departure sequence.
[M10.effect.2] The Aircraft Operator/ Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M10.procedures.1] First step: To inform all relevant partners of the TSAT that has been allocated to the flight.
[M10.procedures.2] The Network Operations is informed by a T-DPI-s for non regulated flights.
[M10.procedures.3] Second step: To check whether the number of TOBT updates exceeds a tolerance defined locally, after TSAT has been issued.
[M10.procedures.4] First: The TSAT will indicate to the partners the time when the start up approval can be expected.
[M10.procedures.5] Network Operations will be informed with a T-DPI-s for non regulated flights.
[M10.procedures.6] No check is performed.
[M10.procedures.7] Second: A check shall be performed to see the number of TOBT updates after TSAT has been issued.
[M10.procedures.8] In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.
[M10.procedures.9] This process is triggered by
[M10.procedures.10] - A defined time (local parameter) before TOBT
[M10.procedures.11] - TOBT update after TSAT issue

[M11.definition.2] This is not to be confused with the time passengers are pre-called to the gate via flight information display systems (FIDS) or public address systems.
### Origin and priority

[M11.origin_and_priority.1] Automatic from airport system or manual input by Aircraft Operator/ Ground Handler.
### Timing

[M11.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M11.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M11.effect.1] When boarding commences it gives the Airport CDM Partners a good indication of whether the TOBT/TSAT will be respected.
### Procedures

[M11.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT).
[M11.procedures.2] Second step: To check whether boarding starts in time to respect TOBT and inform the AO/GH in case TOBT needs to be updated.
[M11.procedures.3] Inform of Actual Start Boarding Time (ASBT) when it occurs.
[M11.procedures.4] At a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status.
[M11.procedures.5] This process is triggered by
[M11.procedures.6] - a time variable <value> minutes before TOBT.
### Operational Status (changes to)

## Milestone 12: Aircraft Ready

### Definition

[M12.definition.1] The time when all doors are closed, boarding bridge removed, push back vehicle connected, ready to taxi immediately upon reception of TWR instructions (ARDT).
### Origin and priority

[M12.origin_and_priority.1] Provided by the Aircraft Operator/ Ground Handler.
### Timing

[M12.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M12.data_quality.1] Data is directly available with an accuracy of +/- 1 minute.
### Effect

[M12.effect.1] ATC refines the pre-departure sequence.
[M12.effect.2] The pilot requests start up just before TSAT, following coordination with the Ground Handler.
[M12.effect.3] (Dispatcher / Supervisor / Redcap).
### Procedures

[M12.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up / push-back.
[M12.procedures.2] Second step: To inform the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).
[M12.procedures.3] Inform of ARDT or RDY confirming that the flight follows the indicated TOBT.
[M12.procedures.4] At TOBT + tolerance the AO/GH are informed that TOBT has passed and there has not been a ready status message yet.
[M12.procedures.5] This procedure is triggered by
[M12.procedures.6] - an input to the Airport CDM Platform.

## Milestone 15: Off-Block

### Definition

[M15.definition.1] AOBT - Actual Off-Block Time.
[M15.definition.2] The time the aircraft pushes back/vacates the parking position (Equivalent to Airline/Handler ATD - Actual Time of Departure ACARS=OUT).
### Origin and priority

[M15.origin_and_priority.1] ACARS equipped aircraft or automated docking systems or ATC systems (e.g. A-SMGCS) or by manual input.
### Timing

[M15.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M15.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M15.effect.1] TTOT updated considering the EXOT.
### Procedures

[M15.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back / taxi from parking position.
[M15.procedures.2] Second step: To check if TTOT changes by more than the agreed tolerance and inform Network Operations.
[M15.procedures.3] Inform of AOBT when it occurs.
[M15.procedures.4] AOBT always triggers an A-DPI message to Network Operations or in the case of remote holding at a defined time prior to TTOT.
[M15.procedures.5] After a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.
[M15.procedures.6] This process is triggered by AOBT detection.
### Operational Status (changes to)

[M15.operational_status.1] OFF-BLOCK
### Action on CDM Operation (ACISP)

[M15.action_on_cdm.1] AOBT recorded
## Milestone 16: Take Off

### Definition

[M16.definition.1] ATOT - Actual Take Off Time.
[M16.definition.2] This is the time that an aircraft takes off from the runway.
[M16.definition.3] (Equivalent to ATC ATD-Actual Time of Departure, ACARS = OFF).
### Origin and priority

[M16.origin_and_priority.1] Provided by ATC system or from ACARS equipped aircraft.
### Timing

[M16.timing.1] The information is directly available as soon as possible after occurrence of the milestone.
### Data Quality

[M16.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M16.effect.1] FSA and MVT messages are sent.
### Procedures

[M16.procedures.1] To inform all relevant Airport CDM Partners about the actual take off.
[M16.procedures.2] An airborne message is generated and the flight is removed from the departure sequence.
[M16.procedures.3] This process is triggered by Tower FDPS, A-SMGCS / Radar detection or ACARS.
### Operational Status (changes to)

[M16.operational_status.1] DEPARTED / TAKE OFF
### Action on CDM Operation (ACISP)

[M16.action_on_cdm.1] ATOT recorded

# The model

class Stakeholder (package Stakeholders): A party that takes part in the CDM process and originates or receives flight information.
  attribute name: String; The identifying name of the stakeholder.

class AircraftOperator (package Stakeholders): The airline (AO) responsible for operating the flight, submitting the ATC Flight Plan, and providing TOBT and other turn-round estimates.
  operation provideTOBT(flight: Flight, value: DateTime): void; The AO/GH provides the TOBT, calculated on the basis of the estimated/defined turn-round period, updated automatically or inserted manually (milestones 6,7,8).
  operation computeTOBTStrategy(flight: Flight): DateTime; The Aircraft Operator integrates his own strategy to compute a TOBT related to the flight, providing the most accurate TOBT taking into account the operational situation (milestone 9).

class GroundHandler (package Stakeholders): The party (GH), possibly including dispatcher/supervisor roles, that manages the turn-round process in coordination with the aircrew and provides TOBT and ready status.
  operation manageTurnRoundProcess(flight: Flight): void; The Ground Handler, in coordination with the aircrew, manages the turn-round process following TOBT confirmation and TSAT issue (milestones 9,10).

class AirTrafficControl (package Stakeholders): The air traffic control units (ATS units, Area Control Centre, Approach Control Unit, Tower) that provide radar detection, issue TSAT/start-up approval, and manage the pre-departure sequence.
  operation issueTSAT(flight: Flight, t: Duration): DateTime; ATC issues the Target Start Up Approval Time t minutes before EOBT, a locally agreed parameter (milestone 10).
  operation approveStartUp(flight: Flight): void; ATC gives the aircraft its start up approval / push-back clearance (milestone 14).
  operation establishPushBackSequence(flight: Flight): void; An accurate TOBT at EOBT-t minutes is a pre-requisite for ATC to establish a push back / pre-departure sequence (milestone 9).
  operation calculateEXOT(flight: Flight): Duration; Following receipt of TOBT, the ATC system calculates and provides the Estimated Taxi-Out Time based on the predicted traffic load, gate/stand location, runway in use, and waiting period at the Holding Position (milestone 9).
  operation refineSequence(flight: Flight): void; ATC refines the pre-departure sequence once the aircraft is ready (milestone 12).
  operation confirmTSATToPilot(flight: Flight): void; ATC confirms TSAT to the pilot in order to maintain the aircraft in the pre-departure sequence (milestone 13).
  operation reSequenceFlight(flight: Flight): void; If start-up approval is not granted at TSAT+tolerance, the flight is re-sequenced (milestone 14).

class NetworkOperations (package Stakeholders): The network operations function that issues CTOT for regulated flights, monitors flight progress, and receives DPI/FUM messages.
  operation issueCTOT(flight: Flight): DateTime; If the flight is regulated, Network Operations issues a CTOT at EOBT-2h, sent to relevant ATS units and the departure aerodrome; CTOT flights usually have priority over unregulated flights (milestone 2).
  operation monitorFlightProgress(flight: Flight): void; Within 3 hours flying time of the destination, Network Operations monitors progress of the flight using ETFMS and sends a Flight Update Message (milestone 3).

class AirportOperator (package Stakeholders): The airport authority / stand-gate management function responsible for the airport slot programme and airport flight data.

class Aircrew (package Stakeholders): The flight crew (pilot) that requests start-up and coordinates with the Ground Handler.
  operation requestStartUp(flight: Flight): void; The pilot requests start up just before TSAT, following coordination with the Ground Handler, by voice or DCL (milestones 12,13,14).

class Flight (package Flights): A single flight movement, arriving or departing, tracked through the sixteen milestones of the CDM turn-round process.
  attribute aircraftRegistration: String; The registration of the aircraft operating the flight, confirmed via the ATC Flight Plan (milestone 1).
  attribute direction: FlightDirection; Whether the flight is the arriving or departing flight of a turn-round (milestone 1).
  attribute operationalStatus: FlightOperationalStatus; The current operational status of the flight, changed at each milestone (e.g. INITIATED, AIRBORNE, FIR, FINAL, LANDED, IN-BLOCK, SEQUENCED, BOARDING, READY, OFF-BLOCK, DEPARTED / TAKE OFF).
  attribute regulated: Boolean; Whether the flight is regulated and has received a CTOT; regulated flights usually have priority over unregulated flights (milestone 2).
  attribute flightReadyTime: Duration; The flight is ready not later than 15 minutes after the planned EOBT (milestone 1).
  operation updateOperationalStatus(newStatus: FlightOperationalStatus): void; Changes the flight's operational status as each milestone occurs.

class TurnRound (package Flights): The turn-round of an aircraft, which normally includes an arriving and a departing flight.
  attribute minimumTurnRoundTime: Duration; MTTT, the minimum/estimated turn-round period used as the basis for TOBT/TTOT calculation, e.g. EIBT+MTTT+EXOT (milestones 2,3,6,7,8).

class ATCFlightPlan (package Flights): The ICAO flight plan submitted to ATC and distributed by IFPS, describing the flight's aerodromes and estimates, corresponding to the airport slot programme.
  attribute type: FlightPlanType; Whether this is a standard flight plan or a repetitive flight plan (RFPL) covering daily or weekly flights (milestone 1).
  attribute departureAerodrome: String; The departure aerodrome (ADEP) of the flight (milestone 1).
  attribute destinationAerodrome: String; The destination aerodrome of the flight (milestone 1).
  attribute sobt: OffBlockTime; The Scheduled Off-Block Time that must be consistent before the first E-DPI is sent (milestone 1).

class AirportSlot (package Flights): The airport slot programme entry that the ATC Flight Plan must correspond to.
  attribute coordinationStatus: SlotCoordinationStatus; Whether the airport is coordinated (outbound flight already known) or non-coordinated (flight plan used to initiate the outbound flight) (milestone 1).

class Aircraft (package Flights): The aircraft assigned to operate the flight, whose type may be updated from the flight plan.
  attribute registration: String; The aircraft registration (milestone 1).
  attribute aircraftType: String; The type of aircraft, which the flight plan may be used to update (milestone 1).

class AirportFlightData (package Flights): The airport's own flight data record checked for consistency against the ATC Flight Plan and Airport Slot.
  attribute gateStandAllocation: String; The airport's recorded gate/stand information for the flight, checked for consistency (milestone 1).

class TimeQuantity (package Timings): A time value describing a flight's progress, carrying its prefix, origin, accuracy, and update time; every successive value is kept rather than overwritten so a turn-round can be analysed afterwards.
  attribute value: DateTime; The time value itself.
  attribute prefix: TimePrefix; Whether this is the scheduled, estimated, target, actual, or calculated value of the event.
  attribute originator: String; Who or what system provided this value, e.g. ATC, AO/GH, ACARS, ATC system.
  attribute accuracy: String; The stated accuracy of the value, e.g. actual times are available with an accuracy of +/- 1 minute.
  attribute updateTime: DateTime; The time this value was recorded.
  operation recordValue(value: DateTime, originator: String, timestamp: DateTime): void; Appends a new time value with its originator and time of update, rather than overwriting the previous value, so the turn-round can be analysed afterwards.

class OffBlockTime (package Timings): The scheduled (SOBT), estimated (EOBT), target (TOBT), or actual (AOBT) off-block time of a flight.
  attribute toleranceWindow: Duration; The locally agreed tolerance window applied to TOBT, e.g. checked t minutes before EOBT, or TSAT/TOBT update tolerance windows (milestones 9,10).

class InBlockTime (package Timings): The estimated (EIBT) or actual (AIBT) in-block time of an arriving flight.
  operation calculateEIBT(eldt: LandingTime, exit: TaxiInTime): DateTime; EIBT is computed using the ELDT and the estimated taxi-in time EXIT (milestone 4); EIBT can also be updated according to ALDT+EXIT (milestone 6).

class LandingTime (package Timings): The estimated (ELDT) or actual (ALDT) landing time of an arriving flight.
  operation calculateELDT(atot: TakeOffTime, estimatedElapsedTime: Duration): DateTime; Using the ATOT, an ELDT can be calculated by using the Estimated Elapsed Time on the FPL (milestone 3).

class TakeOffTime (package Timings): The estimated (ETOT), target (TTOT), calculated (CTOT), or actual (ATOT) take-off time of a departing flight.
  operation calculateTTOT(eibt: InBlockTime, mttt: Duration, exot: TaxiOutTime, eobt: OffBlockTime, tobt: OffBlockTime): DateTime; Calculation basis for TTOT takes into account EIBT+MTTT+EXOT, if later than EOBT+EXOT (milestone 2); in case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT (milestone 3); in the case of manual input of TOBT, this estimate overrides the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT (milestones 2,3).

class StartUpApprovalTime (package Timings): The target (TSAT) or actual (ASAT) start-up approval time.

class StartUpRequestTime (package Timings): The actual start-up request time (ASRT).

class ReadyTime (package Timings): The actual ready time (ARDT), when all doors are closed and the aircraft is ready to taxi upon reception of TWR instructions.

class BoardingTime (package Timings): The actual start boarding time (ASBT), when the gate opens for passengers to physically start boarding.

class GroundHandlingTime (package Timings): The actual commence ground handling time (ACGT); for a normal turn-round ACGT is considered to commence at AIBT, but this milestone applies specifically to first-operation-of-day or long-term parked flights.

class TaxiOutTime (package Timings): The estimated taxi-out time (EXOT), calculated by ATC based on predicted traffic load, gate/stand location, runway in use, and waiting period at the Holding Position.
  attribute duration: Duration; The estimated taxi-out duration used in TTOT calculation (EOBT+EXOT, TOBT+EXOT).

class TaxiInTime (package Timings): The estimated taxi-in time (EXIT) used to compute the estimated in-block time.
  attribute duration: Duration; The estimated taxi-in duration used in EIBT calculation (ELDT+EXIT, ALDT+EXIT).

class Milestone (package Milestones): One of the sixteen defined events of the CDM turn-round process, each with a trigger, timing rule, effect, and procedure.
  attribute definition: String; The document's definition of the milestone.
  attribute trigger: String; What triggers this milestone's procedure, as stated under Procedures.
  attribute timingRule: String; When the milestone normally occurs, as stated under Timing.
  attribute effect: String; The effect described for the milestone.
  attribute resultingStatus: FlightOperationalStatus; The operational status the flight changes to at this milestone.
  operation occur(flight: Flight, timestamp: DateTime): void; Records the occurrence of the milestone for the flight and changes its operational status.
  operation informPartners(flight: Flight): void; Informs all relevant Airport CDM Partners, a step stated under most milestones' procedures.

class FlightPlanActivated (package Milestones): Milestone 1: the ICAO flight plan is submitted to ATC and the Airport CDM Platform is initiated for the flight.
  operation checkConsistency(flightPlan: ATCFlightPlan, slot: AirportSlot, flightData: AirportFlightData): Boolean; Checks consistency between the ATC Flight Plan, Airport Slot, and Airport flight data before the first E-DPI is sent.
  operation confirmFlightToNetworkOperations(flight: Flight): void; Confirms the flight to Network Operations and allows further local processing of the flight.
  operation sendFirstEDPI(flight: Flight): void; Feeds Network Operations with consistent SOBT, aircraft registration, and first destination data; the E-DPI message should not be sent if no or inconsistent information is provided.

class EOBTMinus2Hours (package Milestones): Milestone 2: at EOBT-2hr most flights are known and all regulated flights receive a CTOT from Network Operations.
  operation checkFlightEstimatesConsistency(flight: Flight): Boolean; Checks whether AO/GH flight estimates are consistent with the ATC Flight Plan, before or after take-off from outstation, to verify feasibility of the estimated off-block time at EOBT-2hrs.
  operation sendFirstTDPI(flight: Flight): void; Informs Network Operations about the updated take-off time estimate using a T-DPI message at EOBT-2hrs.
  operation markAsRegulated(flight: Flight): void; Marks appropriate fields as REGULATED for a flight that has received a CTOT.

class TakeOffFromOutstation (package Milestones): Milestone 3: the ATOT from the outstation (ADEP).
  operation checkLandingEstimateConsistency(flight: Flight): Boolean; Checks whether the AO/GH estimated landing time after take-off from outstation is consistent with the outbound ATC Flight Plan.
  operation sendTDPIt(flight: Flight): void; When needed, informs Network Operations about updated take-off time estimates using a T-DPI-t message; a TTOT tolerance of 5 minutes is respected before informing.

class LocalRadarUpdate (package Milestones): Milestone 4: the flight enters the FIR or local airspace of the destination airport.
  operation commenceTOBTProcess(flight: Flight): void; Commences the TOBT process and checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated ELDT.
  operation notifyNetworkOperationsIfTTOTChanges(flight: Flight, tolerance: Duration): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
  operation restrictStandGateChange(flight: Flight): Boolean; Taking into account EXIT, any change to a stand or gate is not preferred after ELDT-30'.

class FinalApproach (package Milestones): Milestone 5: the flight enters the Final Approach phase at the destination airport, usually 2 to 5 minutes from landing.
  operation commenceTOBTProcess(flight: Flight): void; Commences the TOBT process and checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated ELDT.
  operation notifyNetworkOperationsIfTTOTChanges(flight: Flight, tolerance: Duration): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class Landed (package Milestones): Milestone 6: ALDT, the time an aircraft touches down on a runway.
  operation recordALDT(flight: Flight, timestamp: DateTime): void; ALDT triggers an update of downstream estimates: TOBT and TTOT updated automatically or inserted manually by AO/GH, calculated on the basis of the defined turn-round period; EIBT updated according to ALDT+EXIT.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation notifyNetworkOperationsIfTTOTChanges(flight: Flight, tolerance: Duration): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class InBlock (package Milestones): Milestone 7: AIBT, the time an aircraft arrives in-blocks.
  operation recordAIBT(flight: Flight, timestamp: DateTime): void; AIBT triggers an update of downstream estimates: TOBT and TTOT updated automatically or inserted manually by AO/GH, calculated on the basis of the estimated turn-round period.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation notifyNetworkOperationsIfTTOTChanges(flight: Flight, tolerance: Duration): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class GroundHandlingStarted (package Milestones): Milestone 8: commencement of ground handling operations (ACGT), specific to first-operation-of-day or long-term parked flights.
  operation recordACGT(flight: Flight, timestamp: DateTime): void; ACGT triggers an update of downstream estimates: TOBT updated automatically or inserted manually by AO/GH, calculated on the basis of the estimated turn-round period.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation notifyNetworkOperationsIfTTOTChanges(flight: Flight, tolerance: Duration): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class FinalConfirmationOfTOBT (package Milestones): Milestone 9: the time at which the Aircraft Operator or Ground Handler provide their most accurate TOBT, taking into account the operational situation.
  operation confirmTOBT(flight: Flight, t: Duration): void; The AO/GH provide their most accurate TOBT t minutes before EOBT (t a locally agreed parameter), a pre-requisite for ATC to establish the pre-departure sequence prior to TSAT issue.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan; performed at a predefined local time to confirm TOBT prior to TSAT issue.
  operation notifyNetworkOperationsIfTTOTChanges(flight: Flight, tolerance: Duration): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class TSATIssued (package Milestones): Milestone 10: the time ATC issues the Target Start Up Approval Time.
  operation issueTSAT(flight: Flight, t: Duration): void; Informs all relevant partners of the TSAT allocated to the flight, t minutes before EOBT (a locally agreed parameter); stabilises the flight into the pre-departure sequence.
  operation sendTDPIs(flight: Flight): void; Network Operations is informed by a T-DPI-s for non-regulated flights.
  operation checkTOBTUpdateCount(flight: Flight, threshold: Integer): Boolean; Checks whether the number of TOBT updates after TSAT has been issued exceeds a locally defined threshold; if exceeded, the TOBT input is processed according to local procedure.

class BoardingStarts (package Milestones): Milestone 11: the gate is open for passengers to physically start boarding.
  operation recordASBT(flight: Flight, timestamp: DateTime): void; Informs all relevant Airport CDM Partners of the Actual Start Boarding Time when it occurs.
  operation checkBoardingStatus(flight: Flight, minutesBeforeTOBT: Duration): Boolean; At a certain local time before TOBT (e.g. by aircraft type), checks whether boarding starts in time to respect TOBT and informs the AO/GH if TOBT needs to be updated.

class AircraftReady (package Milestones): Milestone 12: the time when all doors are closed, boarding bridge removed, push back vehicle connected, ready to taxi upon reception of TWR instructions (ARDT).
  operation recordARDT(flight: Flight, timestamp: DateTime): void; Informs all relevant Airport CDM Partners of Actual Ready Time and that the aircraft is ready for start up / push-back.
  operation checkReadyStatusReceived(flight: Flight, tolerance: Duration): Boolean; At TOBT + tolerance, informs the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).

class StartUpRequested (package Milestones): Milestone 13: the time that start up is requested (ASRT), based on pilot request.
  operation recordASRT(flight: Flight, timestamp: DateTime): void; Informs all relevant Airport CDM Partners of Actual Start-up Request Time when it occurs.
  operation alertIfNoStartUpRequested(flight: Flight, tsatTolerance: Duration): Boolean; If the start-up request is not made by TSAT + tolerance, informs the AO/GH that no start-up has been requested, and that TOBT should be updated.

class StartUpApproved (package Milestones): Milestone 14: ASAT, the time an aircraft receives its start up approval.
  operation recordASAT(flight: Flight, timestamp: DateTime): void; Informs all relevant Airport CDM Partners of Actual start up approval Time and that the aircraft has received start up / push-back clearance.
  operation checkASATAgainstTSAT(flight: Flight, tolerance: Duration): Boolean; Checks if ASAT is in accordance with TSAT; if start-up approval is not granted at TSAT + tolerance, all relevant partners are informed and the flight is re-sequenced.

class OffBlock (package Milestones): Milestone 15: AOBT, the time the aircraft pushes back / vacates the parking position.
  operation recordAOBT(flight: Flight, timestamp: DateTime): void; Informs all relevant Airport CDM Partners of Actual Off-Block Time and that the aircraft has commenced push-back / taxi from parking position.
  operation sendADPI(flight: Flight): void; AOBT always triggers an A-DPI message to Network Operations, or in the case of remote holding at a defined time prior to TTOT.
  operation checkTTOTChangeAndNotify(flight: Flight, tolerance: Duration): void; After the first A-DPI is sent, checks TTOT updates against the TTOT tolerance before informing Network Operations, with a new A-DPI, of the updated TTOT.

class TakeOff (package Milestones): Milestone 16: ATOT, the time an aircraft takes off from the runway.
  operation recordATOT(flight: Flight, timestamp: DateTime): void; Informs all relevant Airport CDM Partners about the actual take off, triggered by Tower FDPS, A-SMGCS / Radar detection or ACARS.
  operation generateAirborneMessage(flight: Flight): void; An airborne message is generated and the flight is removed from the departure sequence.
  operation sendFSAAndMVT(flight: Flight): void; FSA and MVT messages are sent.

class AirportCDMPlatform (package Systems): The central platform that is initiated for each flight, processes all available information, and holds the CDM operation actions performed at each milestone.
  attribute initiated: Boolean; Whether the platform has been initiated for the flight (milestone 1).
  operation initiateForFlight(flight: Flight): void; The Airport CDM Platform is initiated for this flight, and all available information is processed (milestone 1).
  operation updateField(flight: Flight, fieldName: String, value: DateTime): void; Updates fields such as ELDT, EIBT, ETOT, TOBT, TTOT, AOBT, ATOT as listed under each milestone's Action on CDM Operation.
  operation markFieldAsRegulated(flight: Flight): void; Marks appropriate fields as REGULATED (milestone 2).

class ATCSystem (package Systems): The ATC/radar system, including A-SMGCS and Tower FDPS, that detects a flight crossing FIR/TMA boundaries or levels using its assigned SSR code, and provides ALDT, AIBT, AOBT, and ATOT.
  operation detectFlight(flight: Flight): DateTime; Detects a flight based upon the assigned SSR code when it crosses a defined FIR/ATC boundary (milestone 4) or a defined range/position or level on Final Approach (milestone 5).

class ACARS (package Systems): The aircraft's ACARS system that reports ON/OFF/OUT/IN events, providing ATOT, ALDT, AIBT, and AOBT.

class ETFMS (package Systems): Network Operations' system used to monitor the progress of a flight within 3 hours flying time of the destination and to generate Flight Update Messages.

class IFPS (package Systems): The system that distributes the ATC Flight Plan to all involved ATC units, including departure and destination aerodromes.

class DPIProcess (package Systems): The messaging process that commences correct DPI messaging with Network Operations following flight plan activation.
  operation commenceMessaging(flight: Flight): void; The DPI process commences the correct messaging with Network Operations, if implemented (milestone 1).

class Message (package Messages): A message exchanged between stakeholders and systems in the CDM process.
  attribute sender: String; The party or system that sent the message.
  attribute timestamp: DateTime; When the message was sent.
  attribute content: String; The content carried by the message.

class DPIMessage (package Messages): A Departure Planning Information message sent to Network Operations at defined points of the process.
  attribute dpiType: DPIType; Which kind of DPI message this is: E-DPI, T-DPI, T-DPI-t, T-DPI-s, or A-DPI.

class FUM (package Messages): The Flight Update Message sent by Network Operations providing updates of the flight's progress.

class MVTMessage (package Messages): The movement message sent when a flight takes off.

class FSAMessage (package Messages): The FSA message sent when a flight takes off.

class AirborneMessage (package Messages): The airborne message generated when the flight departs, after which the flight is removed from the departure sequence.
