# The document: sixteen A-CDM milestones, sentences numbered

## Milestone 1: ATC Flight Plan Activated

### Definition

[M1.definition.1] The ICAO flight plan is submitted to ATC.
[M1.definition.2] The Airport CDM Platform is initiated for this flight, and all available information is processed.
### Origin and priority

[M1.origin_and_priority.1] The ATC Flight Plan is submitted by the Aircraft Operator and distributed by the IFPS.
[M1.origin_and_priority.2] All involved ATC units receive the flight plan, including departure and destination aerodromes.
### Timing

[M1.timing.1] Normally this takes place 3 hours before EOBT, however it may be later.
[M1.timing.2] In some cases a repetitive flight plan (RFPL) has been submitted, covering daily or weekly flights.
### Data Quality

[M1.data_quality.1] The ATC Flight Plan corresponds to the airport slot programme.
### Effect

[M1.effect.1] One aircraft turn-round normally includes an arriving and a departing flight, meaning that it will have two related flight plans.
[M1.effect.2] For coordinated airports, the outbound flight is already known.
[M1.effect.3] The flight plan may be used to update certain information such as type of aircraft.
[M1.effect.4] For long distance flights, the ELDT may differ from the airport slot.
[M1.effect.5] For non coordinated airports, the flight plan is used to initiate the outbound flight.
[M1.effect.6] The flight is ready not later than 15 minutes after the planned EOBT.
[M1.effect.7] The DPI process commences the correct messaging with Network Operations (if implemented - see attachment 2 for details).
### Procedures

[M1.procedures.1] To check consistency between ATC Flight Plan, Airport Slot and Airport flight data and then confirm the flight to the Network Operations and allow further local processing of the flight.
[M1.procedures.2] This check shall be performed to verify the consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
[M1.procedures.3] The AO must provide correct information before this first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible.
[M1.procedures.4] The E-DPI message should not be sent if no or inconsistent information is provided.
[M1.procedures.5] This process is triggered by:
[M1.procedures.6] - The first activation of the ATC Flight Plan (earliest EOBT-3 hr), or
[M1.procedures.7] - New or late submissions of the ATC Flight Plan, after cancellation or revised EOBT
### Operational Status (changes to)

[M1.operational_status.1] INITIATED
### Action on CDM Operation (ACISP)

[M1.action_on_cdm.1] ELDT and EIBT updated for an arrival EOBT and ETOT updated for a departure The DPI process commences (if implemented - see section 3.7.3 for details).
## Milestone 2: EOBT - 2 hr

### Definition

[M2.definition.1] At EOBT-2 hr most flights will be known in the Airport CDM Platform including if they are regulated or not.
[M2.definition.2] All regulated flights receive a CTOT from Network Operations.
### Origin and priority

[M2.origin_and_priority.1] The CTOT is issued by the Network Operations and is sent to relevant ATS units as well as the departure aerodrome.
[M2.origin_and_priority.2] CTOT flights usually have a priority over unregulated flights.
### Timing

[M2.timing.1] If the flight is regulated, a CTOT is issued at EOBT-2h.
### Data Quality

[M2.data_quality.1] Not applicable.
### Effect

[M2.effect.1] For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.
### Procedures

[M2.procedures.1] To check (before or after take off from outstation) whether AO/GH flight estimates are consistent with the ATC Flight Plan and to inform Network Operations about the updated take off time estimate, using a T-DPI Message.
[M2.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs.
[M2.procedures.3] At EOBT-2 hrs Network Operations is informed through the first T-DPI message.
[M2.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT.
[M2.procedures.5] In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M2.procedures.6] This procedure is triggered by
[M2.procedures.7] - a time stamp, at EOBT - 2h.
### Operational Status (changes to)

[M2.operational_status.1] N. A.
### Action on CDM Operation (ACISP)

[M2.action_on_cdm.1] ETOT/TTOT/CTOT Mark appropriate fields as REGULATED
## Milestone 3: Take Off from Outstation

### Definition

[M3.definition.1] The ATOT from the outstation (ADEP)
### Origin and priority

[M3.origin_and_priority.1] The outstation provides ATOT to the Network Operations and Aircraft Operator.
### Timing

[M3.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M3.data_quality.1] The accuracy of ATOT is +/- 1 minute.
### Effect

[M3.effect.1] If the departure airport is more than 3hrs flying time from the destination airport the ATOT is received from either the Network Operations FUM or via the Aircraft Operator / Ground Handler.
[M3.effect.2] Using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
[M3.effect.3] If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS and send a Flight Update Message (FUM) that provides updates of the flight's progress.
### Procedures

[M3.procedures.1] To check whether the AO/GH estimated landing time after take off from outstation are consistent with the outbound ATC Flight Plan, and when needed inform the Network Operations about the updated take off time estimates using a T-DPI-t Message.
[M3.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation.
[M3.procedures.3] A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT.
[M3.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT.
[M3.procedures.5] In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT.
[M3.procedures.6] In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M3.procedures.7] This process is triggered by
[M3.procedures.8] - the take off from outstation.
### Operational Status (changes to)

[M3.operational_status.1] AIRBORNE
### Action on CDM Operation (ACISP)

[M3.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 4: Local Radar Update

### Definition

[M4.definition.1] The flight enters the FIR (Flight Information Region) or the local airspace of the destination airport.
### Origin and priority

[M4.origin_and_priority.1] This information is normally available from the Area Control Centre (ACC) or Approach Control Unit that is associated with an airport.
[M4.origin_and_priority.2] The radar system is able to detect a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
### Timing

[M4.timing.1] Dependent upon the position of the airport in relation to the FIR boundary.
### Data Quality

[M4.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M4.effect.1] Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.
[M4.effect.2] The accuracy of ELDT is particularly important at this stage since downstream decisions are taken, such as stand /gate / aircraft changes, preparation of arrival sequence, preparation of ground handling operations, decisions for connecting passengers.
[M4.effect.3] Uncertainty and ELDT non-accuracy at this stage significantly increase risks for bad and last minute decisions and internal disruptions.
[M4.effect.4] The objective to decrease the number of stand and gate changes in the last 30 minutes requires high accuracy regarding departure and arrival times.
[M4.effect.5] Therefore, taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.
[M4.effect.6] The update of TOBT for the related departing flight takes place following this milestone.
[M4.effect.7] Decisions such as the turn-round period, connecting passengers etc are taken and need to be stable at this event.
[M4.effect.8] An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
### Procedures

[M4.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M4.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M4.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M4.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M4.procedures.5] This process is triggered by
[M4.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M4.operational_status.1] FIR
### Action on CDM Operation (ACISP)

[M4.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 5: Final Approach

### Definition

[M5.definition.1] The flight enters the Final Approach phase at the destination airport.
### Origin and priority

[M5.origin_and_priority.1] This information is normally available from ATC.
[M5.origin_and_priority.2] The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range / position or passes/leaves a predetermined level.
### Timing

[M5.timing.1] Dependent upon local parameters that are defined by ATC.
### Data Quality

[M5.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M5.effect.1] Update of the ELDT to determine a new TOBT.
[M5.effect.2] When a flight reaches this stage it is usually between 2 and 5 minutes from landing (depending on the parameter set by ATC).
[M5.effect.3] This is often the prompt for many partners to start moving resources connected with the flight, such as positioning a parking marshal and ground handling services.
### Procedures

[M5.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M5.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M5.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M5.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M5.procedures.5] This process is triggered by
[M5.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M5.operational_status.1] FINAL
### Action on CDM Operation (ACISP)

[M5.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 6: Landed

### Definition

[M6.definition.1] ALDT - Actual Landing Time.
[M6.definition.2] This is the time that an aircraft touches down on a runway.
[M6.definition.3] (Equivalent to ATC ATA - Actual Time of Arrival landing, ACARS=ON).
### Origin and priority

[M6.origin_and_priority.1] Provided by ATC system or by ACARS from equipped aircraft.
### Timing

[M6.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M6.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M6.effect.1] The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator / Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
[M6.effect.2] The EIBT can be updated according to the ALDT +EXIT.
### Procedures

[M6.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M6.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M6.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
[M6.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M6.procedures.5] This process is triggered by
[M6.procedures.6] - Actual Landing Time: ALDT
### Operational Status (changes to)

[M6.operational_status.1] LANDED
### Action on CDM Operation (ACISP)

[M6.action_on_cdm.1] ELDT changes to ALDT, EIBT, TOBT and TTOT updated

## Milestone 9: Final Confirmation of the TOBT

### Definition

[M9.definition.1] The time at which the Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.
### Origin and priority

[M9.origin_and_priority.1] The Aircraft Operator / Ground Handler provides the information.
### Timing

[M9.timing.1] The information is provided t minutes before EOBT (t is a parameter time agreed locally).
### Data Quality

[M9.data_quality.1] Accuracy is agreed locally.
### Effect

[M9.effect.1] The aim of the final TOBT is to give a timely, accurate and reliable assessment of the off-block time.
[M9.effect.2] It is recognised that main benefits of sharing the TOBT are expected in case of disruptions (internal or external).
[M9.effect.3] In such cases, the difference between EOBT (shared by ATC, Network Operations and Stand / Gate Management) and TOBT may be important.
[M9.effect.4] An accurate TOBT at [EOBT-t minutes] is a pre-requisite for ATC to establish a push back / pre-departure sequence.
[M9.effect.5] Emphasis is put on the need for the Aircraft Operator to integrate his own strategy to compute a TOBT related to the flight.
[M9.effect.6] Following the receipt of the TOBT, the ATC system will calculate and provide the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate / stand location, runway in use, and waiting period at the Holding Position, etc. The flight is introduced into the pre-departure sequence.
[M9.effect.7] The Aircraft Operator / Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M9.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M9.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M9.procedures.3] This check should be performed at a predefined time (local parameter) to confirm TOBT prior to TSAT issue and verify feasibility of the ATC Flight Plan estimates given the updated TOBT.
[M9.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M9.procedures.5] This Milestone Process is actually constantly applicable in the CDM Platform, as soon as a TOBT is available.
[M9.procedures.6] However the confirmed TOBT prior to TSAT has special status, where AO/GH check the quality of TOBT before TSAT issue.
### Operational Status (changes to)

[M9.operational_status.1] IN-BLOCK
### Action on CDM Operation (ACISP)

[M9.action_on_cdm.1] This process is triggered by - a new TOBT or TTOT update.
[M9.action_on_cdm.2] No need to confirm an existing TOBT if it has been manually modified before.

### Definition

[M10.definition.1] The time ATC issues the Target Start Up Approval Time
### Origin and priority

[M10.origin_and_priority.1] ATC
### Timing

[M10.timing.1] The information is provided t-minutes before EOBT, where t is a parameter agreed locally
### Data Quality

[M10.data_quality.1] Accuracy is agreed locally.
### Effect

[M10.effect.1] The flight is stabilised into the pre-departure sequence.
[M10.effect.2] The Aircraft Operator/ Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M10.procedures.1] First step: To inform all relevant partners of the TSAT that has been allocated to the flight.
[M10.procedures.2] The Network Operations is informed by a T-DPI-s for non regulated flights.
[M10.procedures.3] Second step: To check whether the number of TOBT updates exceeds a tolerance defined locally, after TSAT has been issued.
[M10.procedures.4] First: The TSAT will indicate to the partners the time when the start up approval can be expected.
[M10.procedures.5] Network Operations will be informed with a T-DPI-s for non regulated flights.
[M10.procedures.6] No check is performed.
[M10.procedures.7] Second: A check shall be performed to see the number of TOBT updates after TSAT has been issued.
[M10.procedures.8] In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.
[M10.procedures.9] This process is triggered by
[M10.procedures.10] - A defined time (local parameter) before TOBT
[M10.procedures.11] - TOBT update after TSAT issue

[M11.definition.2] This is not to be confused with the time passengers are pre-called to the gate via flight information display systems (FIDS) or public address systems.
### Origin and priority

[M11.origin_and_priority.1] Automatic from airport system or manual input by Aircraft Operator/ Ground Handler.
### Timing

[M11.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M11.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M11.effect.1] When boarding commences it gives the Airport CDM Partners a good indication of whether the TOBT/TSAT will be respected.
### Procedures

[M11.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT).
[M11.procedures.2] Second step: To check whether boarding starts in time to respect TOBT and inform the AO/GH in case TOBT needs to be updated.
[M11.procedures.3] Inform of Actual Start Boarding Time (ASBT) when it occurs.
[M11.procedures.4] At a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status.
[M11.procedures.5] This process is triggered by
[M11.procedures.6] - a time variable <value> minutes before TOBT.
### Operational Status (changes to)

## Milestone 12: Aircraft Ready

### Definition

[M12.definition.1] The time when all doors are closed, boarding bridge removed, push back vehicle connected, ready to taxi immediately upon reception of TWR instructions (ARDT).
### Origin and priority

[M12.origin_and_priority.1] Provided by the Aircraft Operator/ Ground Handler.
### Timing

[M12.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M12.data_quality.1] Data is directly available with an accuracy of +/- 1 minute.
### Effect

[M12.effect.1] ATC refines the pre-departure sequence.
[M12.effect.2] The pilot requests start up just before TSAT, following coordination with the Ground Handler.
[M12.effect.3] (Dispatcher / Supervisor / Redcap).
### Procedures

[M12.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up / push-back.
[M12.procedures.2] Second step: To inform the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).
[M12.procedures.3] Inform of ARDT or RDY confirming that the flight follows the indicated TOBT.
[M12.procedures.4] At TOBT + tolerance the AO/GH are informed that TOBT has passed and there has not been a ready status message yet.
[M12.procedures.5] This procedure is triggered by
[M12.procedures.6] - an input to the Airport CDM Platform.

## Milestone 15: Off-Block

### Definition

[M15.definition.1] AOBT - Actual Off-Block Time.
[M15.definition.2] The time the aircraft pushes back/vacates the parking position (Equivalent to Airline/Handler ATD - Actual Time of Departure ACARS=OUT).
### Origin and priority

[M15.origin_and_priority.1] ACARS equipped aircraft or automated docking systems or ATC systems (e.g. A-SMGCS) or by manual input.
### Timing

[M15.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M15.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M15.effect.1] TTOT updated considering the EXOT.
### Procedures

[M15.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back / taxi from parking position.
[M15.procedures.2] Second step: To check if TTOT changes by more than the agreed tolerance and inform Network Operations.
[M15.procedures.3] Inform of AOBT when it occurs.
[M15.procedures.4] AOBT always triggers an A-DPI message to Network Operations or in the case of remote holding at a defined time prior to TTOT.
[M15.procedures.5] After a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.
[M15.procedures.6] This process is triggered by AOBT detection.

## Milestone 16: Take Off

### Definition

[M16.definition.1] ATOT - Actual Take Off Time.
[M16.definition.2] This is the time that an aircraft takes off from the runway.
[M16.definition.3] (Equivalent to ATC ATD-Actual Time of Departure, ACARS = OFF).
### Origin and priority

[M16.origin_and_priority.1] Provided by ATC system or from ACARS equipped aircraft.
### Timing

[M16.timing.1] The information is directly available as soon as possible after occurrence of the milestone.
### Data Quality

[M16.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M16.effect.1] FSA and MVT messages are sent.
### Procedures

[M16.procedures.1] To inform all relevant Airport CDM Partners about the actual take off.
[M16.procedures.2] An airborne message is generated and the flight is removed from the departure sequence.
[M16.procedures.3] This process is triggered by Tower FDPS, A-SMGCS / Radar detection or ACARS.
### Operational Status (changes to)

[M16.operational_status.1] DEPARTED / TAKE OFF
### Action on CDM Operation (ACISP)

[M16.action_on_cdm.1] ATOT recorded

# The model

class AirportCDMPartner (package Stakeholders): A party that takes part in the Airport CDM process and originates or receives process information.
  attribute partnerId: String; Identifier of the stakeholder.
  attribute name: String; Name of the stakeholder organisation.

class AircraftOperator (package Stakeholders): The airline (AO) that operates the flight, submits the ATC Flight Plan and provides estimates such as TOBT.

class GroundHandler (package Stakeholders): The Ground Handler (GH) that, with the Aircraft Operator, manages the turn-round and provides estimates such as TOBT and ARDT.

class ATCUnit (package Stakeholders): An air traffic control unit (ATS, ACC, Approach, or Tower) that provides radar/ATC information and manages the pre-departure sequence.

class NetworkOperations (package Stakeholders): The network management function that issues CTOT, receives DPI messages and monitors flight progress via ETFMS.

class Aircrew (package Stakeholders): The flight crew who coordinate with the Ground Handler and request start-up from ATC.

class Aircraft (package Flights): The physical aircraft assigned to a flight, described by type and registration information carried in the ATC Flight Plan.
  attribute registration: String; Aircraft registration, fed to Network Operations via the first E-DPI.
  attribute aircraftType: String; Type of aircraft, which the flight plan may be used to update.

class Flight (package Flights): An arriving or departing operation of an aircraft turn-round, tracked through the sixteen CDM milestones with its operational status and time quantities.
  attribute flightId: String; Identifier of the flight.
  attribute direction: FlightDirection; Whether the flight is the arrival or the departure leg of the turn-round.
  attribute operationalStatus: FlightOperationalStatus; Status changed by each milestone, e.g. INITIATED, AIRBORNE, FIR, FINAL, LANDED, IN-BLOCK, SEQUENCED, BOARDING, READY, OFF-BLOCK, DEPARTED / TAKE OFF.
  attribute regulated: Boolean; Whether the flight is regulated and has received a CTOT; regulated flights usually have priority over unregulated flights (M2).
  attribute eobt: EOBT; Estimated Off-Block Time of the flight.
  attribute tobt: TOBT; Target Off-Block Time of the flight, appended each time it is updated.
  attribute aobt: AOBT; Actual Off-Block Time recorded at push-back.
  attribute eldt: ELDT; Estimated Landing Time of the flight, updated at multiple milestones.
  attribute eibt: EIBT; Estimated In-Block Time computed from ELDT and EXIT, or ALDT and EXIT.
  attribute aldt: ALDT; Actual Landing Time recorded at touch-down.
  attribute aibt: AIBT; Actual In-Block Time recorded on arrival at the stand.
  attribute etot: ETOT; Estimated Take-Off Time, updated for a departure at M1.
  attribute ttot: TTOT; Target Take-Off Time, recalculated at every milestone from EIBT+MTTT+EXOT or TOBT+EXOT.
  attribute ctot: CTOT; Calculated Take-Off Time issued by Network Operations at EOBT-2h for regulated flights.
  attribute atot: ATOT; Actual Take-Off Time recorded at take-off.
  attribute asbt: ASBT; Actual Start Boarding Time.
  attribute ardt: ARDT; Actual Ready Time when the aircraft is ready to taxi.
  attribute asrt: ASRT; Actual Start-up Request Time.
  attribute asat: ASAT; Actual Start-up Approval Time.
  attribute tsat: TSAT; Target Start-Up Approval Time issued by ATC.
  attribute exot: EXOT; Estimated Taxi-Out Time calculated by ATC based on traffic load, gate/stand location, runway in use and holding-point waiting time.
  attribute exit: EXIT; Estimated Taxi-In Time, used with ELDT/ALDT to compute EIBT.
  attribute mttt: MTTT; Minimum/estimated Turn-Round Time used as basis for TOBT/TTOT calculation.

class TurnRound (package Flights): The aircraft turn-round, normally comprising a related arriving and departing flight, analysed afterwards using the recorded successive time values.
  attribute turnRoundId: String; Identifier of the turn-round.

class ATCFlightPlan (package Flights): The ICAO flight plan submitted by the Aircraft Operator and distributed by the IFPS, against which flight estimates are checked for consistency.
  attribute sobt: DateTime; Scheduled Off-Block Time fed to Network Operations via the first E-DPI.
  attribute departureAerodrome: String; ADEP, distributed to all involved ATC units.
  attribute destinationAerodrome: String; First destination, fed to Network Operations via the first E-DPI.
  attribute isRepetitive: Boolean; Whether the plan is a repetitive flight plan (RFPL) covering daily or weekly flights.

class AirportSlot (package Flights): The airport slot programme entry with which the ATC Flight Plan and airport flight data must be consistent.
  attribute slotTime: DateTime; The slot time allocated to the flight.

class AirportFlightData (package Flights): The airport's own local flight data used together with the ATC Flight Plan and the Airport Slot to check consistency before the first E-DPI.
  attribute data: String; Local airport flight data checked for consistency.

class TimeQuantity (package Timings): A time quantity that describes a flight's progress, with its originator, accuracy and tolerance; every successive value is kept rather than overwritten.
  attribute value: DateTime; The time value of this quantity.
  attribute originator: AirportCDMPartner; The stakeholder or system that provided or updated this value.
  attribute timeOfUpdate: DateTime; When this value was appended.
  attribute accuracy: String; The stated accuracy of the value, e.g. +/- 1 minute.
  operation appendValue(newValue: DateTime, originator: AirportCDMPartner): void; Appends a new value with its originator and time of update rather than overwriting, so the turn-round can be analysed afterwards.

class EOBT (package Timings): Estimated Off-Block Time, the reference against which TOBT and other estimates are compared.

class TOBT (package Timings): Target Off-Block Time provided or confirmed by the AO/GH, used as the basis for TTOT calculation.

class AOBT (package Timings): Actual Off-Block Time, the moment the aircraft pushes back/vacates the parking position.

class ELDT (package Timings): Estimated Landing Time, updated at flight-plan activation, EOBT-2h, take-off, radar detection and final approach.

class EIBT (package Timings): Estimated In-Block Time, computed using ELDT (or ALDT) and the Estimated Taxi-In Time (EXIT).

class ALDT (package Timings): Actual Landing Time, the time an aircraft touches down, accurate to +/- 1 minute.

class AIBT (package Timings): Actual In-Block Time, the time an aircraft arrives in-blocks, accurate to +/- 1 minute.

class ETOT (package Timings): Estimated Take-Off Time, updated for a departure at flight-plan activation.

class TTOT (package Timings): Target Take-Off Time, recalculated at each milestone from EIBT+MTTT+EXOT (or EOBT+EXOT) unless overridden by TOBT+EXOT, and reported to Network Operations when it changes beyond tolerance.

class CTOT (package Timings): Calculated Take-Off Time issued by Network Operations at EOBT-2h for regulated flights.

class ATOT (package Timings): Actual Take-Off Time, the time an aircraft takes off, accurate to +/- 1 minute.

class ASBT (package Timings): Actual Start Boarding Time, when the gate opens for passengers to physically board.

class ARDT (package Timings): Actual Ready Time, when doors are closed, bridge removed and push-back vehicle connected.

class ASRT (package Timings): Actual Start-up Request Time, when the pilot requests start-up.

class ASAT (package Timings): Actual Start-up Approval Time, when the aircraft receives start-up approval.

class TSAT (package Timings): Target Start-Up Approval Time issued by ATC t-minutes before EOBT.

class EXOT (package Timings): Estimated Taxi-Out Time, calculated by the ATC system from predicted traffic load, gate/stand location, runway in use and holding-position waiting period.

class EXIT (package Timings): Estimated Taxi-In Time, used with ELDT/ALDT to compute EIBT and to determine the stand/gate change deadline.

class MTTT (package Timings): The (minimum/estimated) turn-round period used as the basis for TOBT and TTOT calculation after landing/in-block/ground-handling milestones.

class Milestone (package Milestones): One of the sixteen CDM milestone events, each with a defined trigger, timing rule, effect and procedure that checks and updates flight estimates.
  attribute trigger: String; The event(s) that trigger this milestone's process.
  attribute newOperationalStatus: FlightOperationalStatus; The operational status the flight changes to at this milestone.
  attribute accuracy: String; Stated accuracy of the milestone's time data, e.g. +/- 1 minute.
  operation changeOperationalStatus(flight: Flight): void; Changes the flight's operational status as stated for this milestone.

class FlightPlanActivatedMilestone (package Milestones): Milestone 1: the ATC Flight Plan is submitted and the Airport CDM Platform is initiated for the flight.
  operation checkConsistency(flightPlan: ATCFlightPlan, slot: AirportSlot, flightData: AirportFlightData): Boolean; Checks consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
  operation confirmFlightToNetworkOperations(flight: Flight): void; Confirms the flight to Network Operations and allows further local processing, triggered by first activation (earliest EOBT-3hr) or new/late submissions after cancellation or revised EOBT.

class EOBTMinus2hMilestone (package Milestones): Milestone 2: at EOBT-2hr regulated flights receive a CTOT and estimates are checked against the ATC Flight Plan.
  operation checkEstimatesConsistency(flight: Flight): Boolean; Checks whether AO/GH flight estimates are consistent with the ATC Flight Plan, verifying feasibility of the estimated off-block time at EOBT-2hrs.
  operation calculateTTOT(flight: Flight): DateTime; Calculates TTOT from EIBT+MTTT+EXOT if later than EOBT+EXOT, or TOBT+EXOT if TOBT was manually input, overriding the EIBT+MTTT estimate.
  operation markAsRegulated(flight: Flight): void; Marks appropriate fields as REGULATED for flights that receive a CTOT.

class TakeOffFromOutstationMilestone (package Milestones): Milestone 3: the ATOT from the outstation (ADEP) is provided to Network Operations and the Aircraft Operator.
  operation checkEstimatedLandingConsistency(flight: Flight): Boolean; Checks whether AO/GH estimated landing time after outstation take-off is consistent with the outbound ATC Flight Plan.
  operation calculateELDT(atot: ATOT): DateTime; Calculates ELDT using ATOT and the Estimated Elapsed Time on the FPL.
  operation checkTTOTTolerance(flight: Flight): Boolean; Respects a TTOT tolerance of 5 minutes before Network Operations is informed of updated TTOT.

class LocalRadarUpdateMilestone (package Milestones): Milestone 4: the flight enters the FIR or local airspace, detected by radar via the assigned SSR code.
  operation commenceTOBTProcess(flight: Flight): void; Commences the TOBT process and checks whether AO/GH TOBT is consistent with the ATC Flight Plan, given updated ELDT/EIBT.
  operation checkStandGateChangeDeadline(flight: Flight): Boolean; Checks that, taking into account EXIT, any stand or gate change is not preferred after ELDT-30 minutes.
  operation informNetworkOperationsIfTolerated(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class FinalApproachMilestone (package Milestones): Milestone 5: the flight enters the Final Approach phase at the destination airport, typically 2 to 5 minutes from landing.
  operation commenceTOBTProcess(flight: Flight): void; Commences the TOBT process and checks whether AO/GH TOBT is consistent with the ATC Flight Plan given updated ELDT.
  operation informNetworkOperationsIfTolerated(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class LandedMilestone (package Milestones): Milestone 6: ALDT, the time an aircraft touches down, triggers an update of downstream estimates.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether AO/GH TOBT is consistent with the ATC Flight Plan given ALDT.
  operation calculateEIBT(aldt: ALDT, exit: EXIT): DateTime; Updates EIBT according to ALDT+EXIT.
  operation informNetworkOperationsIfTolerated(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class InBlockMilestone (package Milestones): Milestone 7: AIBT, the time an aircraft arrives in-blocks, triggers an update of downstream estimates.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether AO/GH TOBT is consistent with the ATC Flight Plan given AIBT.
  operation informNetworkOperationsIfTolerated(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class GroundHandlingStartedMilestone (package Milestones): Milestone 8: ACGT, the commencement of ground handling operations, specific to first-of-day or long-term-parked flights, triggers an update of TOBT.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether AO/GH TOBT is consistent with the ATC Flight Plan given ACGT.
  operation informNetworkOperationsIfTolerated(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class FinalTOBTConfirmationMilestone (package Milestones): Milestone 9: the time at which AO/GH provide their most accurate TOBT, t minutes before EOBT, prior to TSAT issue.
  operation checkTOBTConsistency(flight: Flight): Boolean; Checks whether AO/GH TOBT is consistent with the ATC Flight Plan at the predefined local time before TSAT issue, triggered by a new TOBT or TTOT update.
  operation calculateEXOT(flight: Flight): DateTime; Following receipt of TOBT, the ATC system calculates EXOT based on predicted traffic load, gate/stand location, runway in use and holding-position waiting period.
  operation informNetworkOperationsIfTolerated(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class TSATIssuedMilestone (package Milestones): Milestone 10: ATC issues the Target Start-Up Approval Time, t minutes before EOBT.
  operation informPartnersOfTSAT(flight: Flight): void; Informs all relevant partners of the TSAT allocated to the flight; Network Operations is informed by a T-DPI-s for non-regulated flights.
  operation checkTOBTUpdateCount(flight: Flight): Boolean; Checks whether the number of TOBT updates after TSAT has been issued exceeds a locally defined tolerance; if exceeded, TOBT input is processed per local procedure.

class BoardingStartsMilestone (package Milestones): Milestone 11: the gate opens for passengers to physically start boarding.
  operation informPartnersOfASBT(flight: Flight): void; Informs all relevant Airport CDM Partners of Actual Start Boarding Time when it occurs.
  operation checkBoardingStatus(flight: Flight): Boolean; At a locally defined time before TOBT, checks the boarding status and informs the AO/GH if TOBT needs updating.

class AircraftReadyMilestone (package Milestones): Milestone 12: all doors closed, boarding bridge removed and push-back vehicle connected, ready to taxi.
  operation informPartnersOfARDT(flight: Flight): void; Informs all relevant Airport CDM Partners of ARDT/RDY confirming the flight follows the indicated TOBT.
  operation checkReadyStatusReceived(flight: Flight): Boolean; At TOBT + tolerance, informs the AO/GH that TOBT has passed and no ready status message has yet been received.

class StartUpRequestedMilestone (package Milestones): Milestone 13: ATC records the time that start-up is requested, based on pilot request.
  operation informPartnersOfASRT(flight: Flight): void; Informs all relevant Airport CDM Partners of Actual Start-up Request Time when it occurs.
  operation alertIfNoStartUpRequest(flight: Flight): Boolean; If start-up request is not made by TSAT + tolerance, alerts partners and informs AO/GH that TOBT should be updated.

class StartUpApprovedMilestone (package Milestones): Milestone 14: ASAT, the time an aircraft receives its start-up approval.
  operation informPartnersOfASAT(flight: Flight): void; Informs all relevant Airport CDM Partners of Actual Start-up Approval Time and that push-back clearance has been received.
  operation checkASATAgainstTSAT(flight: Flight): Boolean; Checks if ASAT is in accordance with TSAT; if not granted at TSAT + tolerance, all relevant partners are informed and the flight is re-sequenced.

class OffBlockMilestone (package Milestones): Milestone 15: AOBT, the time the aircraft pushes back/vacates the parking position.
  operation informPartnersOfAOBT(flight: Flight): void; Informs all relevant Airport CDM Partners of AOBT and that push-back/taxi has commenced; AOBT always triggers an A-DPI message to Network Operations, or at a defined time prior to TTOT in case of remote holding.
  operation checkTTOTToleranceAndInform(flight: Flight): Boolean; After the first A-DPI is sent, checks TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.

class TakeOffMilestone (package Milestones): Milestone 16: ATOT, the time an aircraft takes off from the runway.
  operation informPartnersOfATOT(flight: Flight): void; Informs all relevant Airport CDM Partners about the actual take-off, generates an airborne message, and removes the flight from the departure sequence.

class AirportCDMPlatform (package Systems): The central system, initiated for each flight, that holds all available flight information, performs the milestone checks and records the CDM Operation actions (ACISP).
  attribute platformId: String; Identifier of the CDM Platform instance for the flight.
  operation updateELDTAndEOBTData(flight: Flight): void; M1 ACISP: updates ELDT and EIBT for an arrival, and EOBT and ETOT for a departure.
  operation updateETOTTTOTCTOT(flight: Flight): void; M2 ACISP: updates ETOT/TTOT/CTOT and marks appropriate fields as REGULATED.
  operation updateAfterOutstationTakeOff(flight: Flight): void; M3 ACISP: updates ELDT, EIBT, TOBT and TTOT.
  operation updateAfterRadarDetection(flight: Flight): void; M4 ACISP: updates ELDT, EIBT, TOBT and TTOT.
  operation updateAfterFinalApproach(flight: Flight): void; M5 ACISP: updates ELDT, EIBT, TOBT and TTOT.
  operation updateAfterLanding(flight: Flight): void; M6 ACISP: changes ELDT to ALDT and updates EIBT, TOBT and TTOT.
  operation updateAfterInBlock(flight: Flight): void; M7 ACISP: changes EIBT to AIBT and updates TOBT and TTOT.
  operation updateAfterGroundHandlingStart(flight: Flight): void; M8 ACISP: updates ETTT/TOBT and TTOT.
  operation recordAOBT(flight: Flight): void; M15 ACISP: records AOBT.
  operation recordATOT(flight: Flight): void; M16 ACISP: records ATOT.

class IFPS (package Systems): The system that distributes the submitted ATC Flight Plan to all involved ATC units.
  operation distributeFlightPlan(flightPlan: ATCFlightPlan): void; Distributes the ATC Flight Plan submitted by the Aircraft Operator to all involved ATC units.

class ETFMS (package Systems): The Network Operations system that monitors flight progress and generates Flight Update Messages when within 3 hours flying time of destination.
  operation monitorProgress(flight: Flight): void; Monitors progress of the flight and sends a FUM providing updates of the flight's progress.

class RadarSystem (package Systems): The ATC radar system that detects a flight by its assigned SSR code at defined FIR/TMA boundaries or on final approach.
  operation detectFlight(flight: Flight): void; Detects the flight crossing a defined FIR/ATC boundary, range/position, or level.

class ACARS (package Systems): The aircraft communication system that can provide ALDT, AIBT, AOBT and ATOT (ON/IN/OUT/OFF).

class DPIProcess (package Systems): The Departure Planning Information process that commences correct messaging with Network Operations if implemented.
  operation sendEDPI(flight: Flight): void; Sends the first E-DPI message, not sent if no or inconsistent information is provided; feeds Network Operations with consistent SOBT, aircraft registration and first destination.
  operation sendTDPI(flight: Flight): void; At EOBT-2hrs, informs Network Operations through the first T-DPI message with the updated take-off time estimate.
  operation sendTDPIt(flight: Flight): void; Informs Network Operations about updated take-off time estimates using a T-DPI-t message after outstation take-off, if TTOT tolerance exceeded.
  operation sendTDPIs(flight: Flight): void; Informs Network Operations with a T-DPI-s for non-regulated flights when TSAT is issued.
  operation sendADPI(flight: Flight): void; AOBT always triggers an A-DPI message to Network Operations, or a new A-DPI when TTOT changes beyond tolerance.

class Message (package Messages): A message exchanged between Airport CDM stakeholders and systems.
  attribute sender: String; Sender of the message.
  attribute timestamp: DateTime; Time the message was sent.

class DPIMessage (package Messages): A Departure Planning Information message sent to Network Operations at defined points in the DPI process.

class EDPIMessage (package Messages): The first E-DPI message, feeding Network Operations with consistent SOBT, aircraft registration and first destination data as early as possible.

class TDPIMessage (package Messages): The T-DPI message informing Network Operations of the updated take-off time estimate at EOBT-2hrs.

class TDPItMessage (package Messages): The T-DPI-t message informing Network Operations of updated take-off time estimates after outstation take-off.

class TDPIsMessage (package Messages): The T-DPI-s message informing Network Operations of TSAT for non-regulated flights.

class ADPIMessage (package Messages): The A-DPI message triggered by AOBT and sent to Network Operations when TTOT changes beyond tolerance.

class FUMMessage (package Messages): The Flight Update Message sent by Network Operations providing updates of the flight's progress, used to update ELDT for inbound flights.

class FSAMessage (package Messages): The FSA message sent after take-off.

class MVTMessage (package Messages): The MVT (movement) message sent after take-off.
