# The document: sixteen A-CDM milestones, sentences numbered

## Milestone 1: ATC Flight Plan Activated

### Definition

[M1.definition.1] The ICAO flight plan is submitted to ATC.
[M1.definition.2] The Airport CDM Platform is initiated for this flight, and all available information is processed.
### Origin and priority

[M1.origin_and_priority.1] The ATC Flight Plan is submitted by the Aircraft Operator and distributed by the IFPS.
[M1.origin_and_priority.2] All involved ATC units receive the flight plan, including departure and destination aerodromes.
### Timing

[M1.timing.1] Normally this takes place 3 hours before EOBT, however it may be later.
[M1.timing.2] In some cases a repetitive flight plan (RFPL) has been submitted, covering daily or weekly flights.
### Data Quality

[M1.data_quality.1] The ATC Flight Plan corresponds to the airport slot programme.
### Effect

[M1.effect.1] One aircraft turn-round normally includes an arriving and a departing flight, meaning that it will have two related flight plans.
[M1.effect.2] For coordinated airports, the outbound flight is already known.
[M1.effect.3] The flight plan may be used to update certain information such as type of aircraft.
[M1.effect.4] For long distance flights, the ELDT may differ from the airport slot.
[M1.effect.5] For non coordinated airports, the flight plan is used to initiate the outbound flight.
[M1.effect.6] The flight is ready not later than 15 minutes after the planned EOBT.
[M1.effect.7] The DPI process commences the correct messaging with Network Operations (if implemented - see attachment 2 for details).
### Procedures

[M1.procedures.1] To check consistency between ATC Flight Plan, Airport Slot and Airport flight data and then confirm the flight to the Network Operations and allow further local processing of the flight.
[M1.procedures.2] This check shall be performed to verify the consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
[M1.procedures.3] The AO must provide correct information before this first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible.
[M1.procedures.4] The E-DPI message should not be sent if no or inconsistent information is provided.
[M1.procedures.5] This process is triggered by:
[M1.procedures.6] - The first activation of the ATC Flight Plan (earliest EOBT-3 hr), or
[M1.procedures.7] - New or late submissions of the ATC Flight Plan, after cancellation or revised EOBT
### Operational Status (changes to)

[M1.operational_status.1] INITIATED
### Action on CDM Operation (ACISP)

[M1.action_on_cdm.1] ELDT and EIBT updated for an arrival EOBT and ETOT updated for a departure The DPI process commences (if implemented - see section 3.7.3 for details).
## Milestone 2: EOBT - 2 hr

### Definition

[M2.definition.1] At EOBT-2 hr most flights will be known in the Airport CDM Platform including if they are regulated or not.
[M2.definition.2] All regulated flights receive a CTOT from Network Operations.
### Origin and priority

[M2.origin_and_priority.1] The CTOT is issued by the Network Operations and is sent to relevant ATS units as well as the departure aerodrome.
[M2.origin_and_priority.2] CTOT flights usually have a priority over unregulated flights.
### Timing

[M2.timing.1] If the flight is regulated, a CTOT is issued at EOBT-2h.
### Data Quality

[M2.data_quality.1] Not applicable.
### Effect

[M2.effect.1] For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.
### Procedures

[M2.procedures.1] To check (before or after take off from outstation) whether AO/GH flight estimates are consistent with the ATC Flight Plan and to inform Network Operations about the updated take off time estimate, using a T-DPI Message.
[M2.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs.
[M2.procedures.3] At EOBT-2 hrs Network Operations is informed through the first T-DPI message.
[M2.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT.
[M2.procedures.5] In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M2.procedures.6] This procedure is triggered by
[M2.procedures.7] - a time stamp, at EOBT - 2h.
### Operational Status (changes to)

[M2.operational_status.1] N. A.
### Action on CDM Operation (ACISP)

[M2.action_on_cdm.1] ETOT/TTOT/CTOT Mark appropriate fields as REGULATED
## Milestone 3: Take Off from Outstation

### Definition

[M3.definition.1] The ATOT from the outstation (ADEP)
### Origin and priority

[M3.origin_and_priority.1] The outstation provides ATOT to the Network Operations and Aircraft Operator.
### Timing

[M3.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M3.data_quality.1] The accuracy of ATOT is +/- 1 minute.
### Effect

[M3.effect.1] If the departure airport is more than 3hrs flying time from the destination airport the ATOT is received from either the Network Operations FUM or via the Aircraft Operator / Ground Handler.
[M3.effect.2] Using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
[M3.effect.3] If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS and send a Flight Update Message (FUM) that provides updates of the flight's progress.
### Procedures

[M3.procedures.1] To check whether the AO/GH estimated landing time after take off from outstation are consistent with the outbound ATC Flight Plan, and when needed inform the Network Operations about the updated take off time estimates using a T-DPI-t Message.
[M3.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation.
[M3.procedures.3] A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT.
[M3.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT.
[M3.procedures.5] In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT.
[M3.procedures.6] In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M3.procedures.7] This process is triggered by
[M3.procedures.8] - the take off from outstation.
### Operational Status (changes to)

[M3.operational_status.1] AIRBORNE
### Action on CDM Operation (ACISP)

[M3.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 4: Local Radar Update

### Definition

[M4.definition.1] The flight enters the FIR (Flight Information Region) or the local airspace of the destination airport.
### Origin and priority

[M4.origin_and_priority.1] This information is normally available from the Area Control Centre (ACC) or Approach Control Unit that is associated with an airport.
[M4.origin_and_priority.2] The radar system is able to detect a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
### Timing

[M4.timing.1] Dependent upon the position of the airport in relation to the FIR boundary.
### Data Quality

[M4.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M4.effect.1] Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.
[M4.effect.2] The accuracy of ELDT is particularly important at this stage since downstream decisions are taken, such as stand /gate / aircraft changes, preparation of arrival sequence, preparation of ground handling operations, decisions for connecting passengers.
[M4.effect.3] Uncertainty and ELDT non-accuracy at this stage significantly increase risks for bad and last minute decisions and internal disruptions.
[M4.effect.4] The objective to decrease the number of stand and gate changes in the last 30 minutes requires high accuracy regarding departure and arrival times.
[M4.effect.5] Therefore, taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.
[M4.effect.6] The update of TOBT for the related departing flight takes place following this milestone.
[M4.effect.7] Decisions such as the turn-round period, connecting passengers etc are taken and need to be stable at this event.
[M4.effect.8] An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
### Procedures

[M4.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M4.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M4.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M4.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M4.procedures.5] This process is triggered by
[M4.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M4.operational_status.1] FIR
### Action on CDM Operation (ACISP)

[M4.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 5: Final Approach

### Definition

[M5.definition.1] The flight enters the Final Approach phase at the destination airport.
### Origin and priority

[M5.origin_and_priority.1] This information is normally available from ATC.
[M5.origin_and_priority.2] The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range / position or passes/leaves a predetermined level.
### Timing

[M5.timing.1] Dependent upon local parameters that are defined by ATC.
### Data Quality

[M5.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M5.effect.1] Update of the ELDT to determine a new TOBT.
[M5.effect.2] When a flight reaches this stage it is usually between 2 and 5 minutes from landing (depending on the parameter set by ATC).
[M5.effect.3] This is often the prompt for many partners to start moving resources connected with the flight, such as positioning a parking marshal and ground handling services.
### Procedures

[M5.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M5.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M5.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M5.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M5.procedures.5] This process is triggered by
[M5.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M5.operational_status.1] FINAL
### Action on CDM Operation (ACISP)

[M5.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 6: Landed

### Definition

[M6.definition.1] ALDT - Actual Landing Time.
[M6.definition.2] This is the time that an aircraft touches down on a runway.
[M6.definition.3] (Equivalent to ATC ATA - Actual Time of Arrival landing, ACARS=ON).
### Origin and priority

[M6.origin_and_priority.1] Provided by ATC system or by ACARS from equipped aircraft.
### Timing

[M6.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M6.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M6.effect.1] The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator / Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
[M6.effect.2] The EIBT can be updated according to the ALDT +EXIT.
### Procedures

[M6.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M6.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M6.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
[M6.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M6.procedures.5] This process is triggered by
[M6.procedures.6] - Actual Landing Time: ALDT
### Operational Status (changes to)

[M6.operational_status.1] LANDED
### Action on CDM Operation (ACISP)

[M6.action_on_cdm.1] ELDT changes to ALDT, EIBT, TOBT and TTOT updated

## Milestone 9: Final Confirmation of the TOBT

### Definition

[M9.definition.1] The time at which the Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.
### Origin and priority

[M9.origin_and_priority.1] The Aircraft Operator / Ground Handler provides the information.
### Timing

[M9.timing.1] The information is provided t minutes before EOBT (t is a parameter time agreed locally).
### Data Quality

[M9.data_quality.1] Accuracy is agreed locally.
### Effect

[M9.effect.1] The aim of the final TOBT is to give a timely, accurate and reliable assessment of the off-block time.
[M9.effect.2] It is recognised that main benefits of sharing the TOBT are expected in case of disruptions (internal or external).
[M9.effect.3] In such cases, the difference between EOBT (shared by ATC, Network Operations and Stand / Gate Management) and TOBT may be important.
[M9.effect.4] An accurate TOBT at [EOBT-t minutes] is a pre-requisite for ATC to establish a push back / pre-departure sequence.
[M9.effect.5] Emphasis is put on the need for the Aircraft Operator to integrate his own strategy to compute a TOBT related to the flight.
[M9.effect.6] Following the receipt of the TOBT, the ATC system will calculate and provide the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate / stand location, runway in use, and waiting period at the Holding Position, etc. The flight is introduced into the pre-departure sequence.
[M9.effect.7] The Aircraft Operator / Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M9.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M9.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M9.procedures.3] This check should be performed at a predefined time (local parameter) to confirm TOBT prior to TSAT issue and verify feasibility of the ATC Flight Plan estimates given the updated TOBT.
[M9.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M9.procedures.5] This Milestone Process is actually constantly applicable in the CDM Platform, as soon as a TOBT is available.
[M9.procedures.6] However the confirmed TOBT prior to TSAT has special status, where AO/GH check the quality of TOBT before TSAT issue.
### Operational Status (changes to)

[M9.operational_status.1] IN-BLOCK
### Action on CDM Operation (ACISP)

[M9.action_on_cdm.1] This process is triggered by - a new TOBT or TTOT update.
[M9.action_on_cdm.2] No need to confirm an existing TOBT if it has been manually modified before.

### Definition

[M10.definition.1] The time ATC issues the Target Start Up Approval Time
### Origin and priority

[M10.origin_and_priority.1] ATC
### Timing

[M10.timing.1] The information is provided t-minutes before EOBT, where t is a parameter agreed locally
### Data Quality

[M10.data_quality.1] Accuracy is agreed locally.
### Effect

[M10.effect.1] The flight is stabilised into the pre-departure sequence.
[M10.effect.2] The Aircraft Operator/ Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M10.procedures.1] First step: To inform all relevant partners of the TSAT that has been allocated to the flight.
[M10.procedures.2] The Network Operations is informed by a T-DPI-s for non regulated flights.
[M10.procedures.3] Second step: To check whether the number of TOBT updates exceeds a tolerance defined locally, after TSAT has been issued.
[M10.procedures.4] First: The TSAT will indicate to the partners the time when the start up approval can be expected.
[M10.procedures.5] Network Operations will be informed with a T-DPI-s for non regulated flights.
[M10.procedures.6] No check is performed.
[M10.procedures.7] Second: A check shall be performed to see the number of TOBT updates after TSAT has been issued.
[M10.procedures.8] In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.
[M10.procedures.9] This process is triggered by
[M10.procedures.10] - A defined time (local parameter) before TOBT
[M10.procedures.11] - TOBT update after TSAT issue

[M11.definition.2] This is not to be confused with the time passengers are pre-called to the gate via flight information display systems (FIDS) or public address systems.
### Origin and priority

[M11.origin_and_priority.1] Automatic from airport system or manual input by Aircraft Operator/ Ground Handler.
### Timing

[M11.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M11.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M11.effect.1] When boarding commences it gives the Airport CDM Partners a good indication of whether the TOBT/TSAT will be respected.
### Procedures

[M11.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT).
[M11.procedures.2] Second step: To check whether boarding starts in time to respect TOBT and inform the AO/GH in case TOBT needs to be updated.
[M11.procedures.3] Inform of Actual Start Boarding Time (ASBT) when it occurs.
[M11.procedures.4] At a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status.
[M11.procedures.5] This process is triggered by
[M11.procedures.6] - a time variable <value> minutes before TOBT.
### Operational Status (changes to)

## Milestone 12: Aircraft Ready

### Definition

[M12.definition.1] The time when all doors are closed, boarding bridge removed, push back vehicle connected, ready to taxi immediately upon reception of TWR instructions (ARDT).
### Origin and priority

[M12.origin_and_priority.1] Provided by the Aircraft Operator/ Ground Handler.
### Timing

[M12.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M12.data_quality.1] Data is directly available with an accuracy of +/- 1 minute.
### Effect

[M12.effect.1] ATC refines the pre-departure sequence.
[M12.effect.2] The pilot requests start up just before TSAT, following coordination with the Ground Handler.
[M12.effect.3] (Dispatcher / Supervisor / Redcap).
### Procedures

[M12.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up / push-back.
[M12.procedures.2] Second step: To inform the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).
[M12.procedures.3] Inform of ARDT or RDY confirming that the flight follows the indicated TOBT.
[M12.procedures.4] At TOBT + tolerance the AO/GH are informed that TOBT has passed and there has not been a ready status message yet.
[M12.procedures.5] This procedure is triggered by
[M12.procedures.6] - an input to the Airport CDM Platform.

## Milestone 15: Off-Block

### Definition

[M15.definition.1] AOBT - Actual Off-Block Time.
[M15.definition.2] The time the aircraft pushes back/vacates the parking position (Equivalent to Airline/Handler ATD - Actual Time of Departure ACARS=OUT).
### Origin and priority

[M15.origin_and_priority.1] ACARS equipped aircraft or automated docking systems or ATC systems (e.g. A-SMGCS) or by manual input.
### Timing

[M15.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M15.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M15.effect.1] TTOT updated considering the EXOT.
### Procedures

[M15.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back / taxi from parking position.
[M15.procedures.2] Second step: To check if TTOT changes by more than the agreed tolerance and inform Network Operations.
[M15.procedures.3] Inform of AOBT when it occurs.
[M15.procedures.4] AOBT always triggers an A-DPI message to Network Operations or in the case of remote holding at a defined time prior to TTOT.
[M15.procedures.5] After a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.
[M15.procedures.6] This process is triggered by AOBT detection.
### Operational Status (changes to)

[M15.operational_status.1] OFF-BLOCK
### Action on CDM Operation (ACISP)

[M15.action_on_cdm.1] AOBT recorded
## Milestone 16: Take Off

### Definition

[M16.definition.1] ATOT - Actual Take Off Time.
[M16.definition.2] This is the time that an aircraft takes off from the runway.
[M16.definition.3] (Equivalent to ATC ATD-Actual Time of Departure, ACARS = OFF).
### Origin and priority

[M16.origin_and_priority.1] Provided by ATC system or from ACARS equipped aircraft.
### Timing

[M16.timing.1] The information is directly available as soon as possible after occurrence of the milestone.
### Data Quality

[M16.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M16.effect.1] FSA and MVT messages are sent.
### Procedures

[M16.procedures.1] To inform all relevant Airport CDM Partners about the actual take off.
[M16.procedures.2] An airborne message is generated and the flight is removed from the departure sequence.
[M16.procedures.3] This process is triggered by Tower FDPS, A-SMGCS / Radar detection or ACARS.
### Operational Status (changes to)

[M16.operational_status.1] DEPARTED / TAKE OFF
### Action on CDM Operation (ACISP)

[M16.action_on_cdm.1] ATOT recorded

# The model

class CdmPartner (package Stakeholders): A party that takes part in the Airport CDM process and originates or receives information about a flight.
  attribute name: String; Identifies the CDM partner.
  operation receiveNotification(information: String): void; Receives information relayed by a milestone process, e.g. 'inform all relevant Airport CDM Partners'.

class AircraftOperator (package Stakeholders): The airline that submits the ATC Flight Plan and provides estimates such as TOBT.
  operation submitFlightPlan(flightPlan: AtcFlightPlan): void; Submits the ICAO ATC Flight Plan; the AO must provide correct information before the first E-DPI (Milestone 1).
  operation provideTobt(flight: Flight, value: DateTime): void; Provides the most accurate TOBT taking into account the operational situation, integrating own strategy to compute TOBT (Milestone 9).

class GroundHandler (package Stakeholders): The party that undertakes ground handling operations and provides ready and TOBT-related information.
  operation commenceGroundHandling(flight: Flight): void; Provides the Actual Commence of Ground Handling time (ACGT) (Milestone 8).
  operation provideArdt(flight: Flight): void; Provides the Actual Ready Time when the aircraft is ready for start up/push-back (Milestone 12).

class AtcUnit (package Stakeholders): An air traffic control unit (ACC, Approach, Tower) that receives the flight plan, issues TSAT, and approves start-up.
  attribute unitType: String; e.g. ACC, Approach Control Unit, Tower/TWR FDPS.
  operation issueTsat(flight: Flight): void; Issues the Target Start-Up Approval Time t-minutes before EOBT, t agreed locally (Milestone 10).
  operation confirmTsatToPilot(flight: Flight): void; Confirms TSAT to the pilot in order to maintain the aircraft in the pre-departure sequence (Milestone 13).
  operation approveStartUp(flight: Flight): void; Grants start-up approval / push-back clearance (Milestone 14).

class NetworkOperations (package Stakeholders): The network management function that issues CTOT, receives DPI messages, and monitors flight progress.
  operation issueCtot(flight: Flight): DateTime; Issues a CTOT at EOBT-2hr to relevant ATS units and the departure aerodrome for regulated flights (Milestone 2).
  operation confirmFlight(flight: Flight): void; Confirms the flight following consistency checking, allowing further local processing (Milestone 1).

class Outstation (package Stakeholders): The departure aerodrome (ADEP) of an inbound flight, which provides the ATOT for that flight.
  operation provideAtot(flight: Flight): DateTime; Provides the ATOT from the outstation, available with accuracy +/- 1 minute (Milestone 3).

class Flight (package Flights): An arriving or departing flight tracked through the CDM process, carrying its operational status and time quantities.
  attribute flightId: String; Identifies the flight.
  attribute direction: String; Arrival or departure leg of a turn-round.
  attribute operationalStatus: FlightOperationalStatus; The status set by each milestone, e.g. INITIATED, AIRBORNE, LANDED, SEQUENCED, DEPARTED/TAKE OFF.
  attribute exot: Duration; Estimated Taxi-Out Time calculated by ATC based on predicted traffic load, gate/stand location, runway in use, and holding position waiting period (Milestone 9).
  attribute exit: Duration; Estimated taxi-in time used with ELDT to compute EIBT and, with ALDT, to update EIBT (Milestones 4, 6).
  attribute sobt: ScheduledTime; Scheduled Off-Block Time shared by ATC, Network Operations and Stand/Gate Management (Milestone 9).
  attribute eobt: EstimatedTime; Estimated Off-Block Time used as the reference for the process timeline (Milestones 1,2,9).
  attribute tobt: TargetTime; Target Off-Block Time, entered by AO/GH or calculated automatically, updated at multiple milestones.
  attribute aobt: ActualTime; Actual Off-Block Time, when the aircraft pushes back/vacates the parking position (Milestone 15).
  attribute eldt: EstimatedTime; Estimated Landing Time, updated using ATOT and Estimated Elapsed Time, and by FUM messages and radar (Milestones 1,2,3,4,5).
  attribute aldt: ActualTime; Actual Landing Time, accuracy +/- 1 minute (Milestone 6).
  attribute eibt: EstimatedTime; Estimated In-Block Time computed using ELDT and estimated taxi-in time, or ALDT+EXIT (Milestones 1,4,6).
  attribute aibt: ActualTime; Actual In-Block Time, accuracy +/- 1 minute (Milestone 7).
  attribute etot: EstimatedTime; Estimated Take-Off Time updated for a departure at flight plan activation (Milestone 1).
  attribute ttot: TargetTime; Target Take-Off Time, calculated basis EIBT+MTTT+EXOT or TOBT+EXOT, updated with a tolerance before Network Operations is informed (Milestones 2-15).
  attribute ctot: CalculatedTime; Calculated Take-Off Time issued by Network Operations for regulated flights at EOBT-2hr (Milestone 2).
  attribute atot: ActualTime; Actual Take-Off Time, from outstation (Milestone 3) or at departure (Milestone 16), accuracy +/- 1 minute.
  attribute acgt: ActualTime; Actual Commence of Ground Handling Time, accuracy +/- 1 minute (Milestone 8).
  attribute asbt: ActualTime; Actual Start Boarding Time, accuracy +/- 1 minute (Milestone 11).
  attribute ardt: ActualTime; Actual Ready Time, accuracy +/- 1 minute (Milestone 12).
  attribute asrt: ActualTime; Actual Start-Up Request Time, accuracy +/- 1 minute (Milestone 13).
  attribute asat: ActualTime; Actual Start-Up Approval Time, accuracy +/- 1 minute (Milestone 14).

class TurnRound (package Flights): An aircraft turn-round normally including an arriving and a departing flight, each with two related flight plans.
  attribute mttt: Duration; Minimum/estimated turn-round period used to calculate TOBT and TTOT for the departing flight (Milestones 6,7,8).

class Aircraft (package Flights): The physical aircraft operating a flight, whose type and registration may be updated from the flight plan.
  attribute registration: String; Aircraft registration provided before the first E-DPI (Milestone 1).
  attribute type: String; Type of aircraft, which may be updated from the ATC Flight Plan (Milestone 1).

class AtcFlightPlan (package Flights): The ICAO flight plan submitted by the Aircraft Operator and distributed by IFPS, corresponding to the airport slot programme.
  attribute departureAerodrome: String; Departure aerodrome (ADEP) named in the flight plan.
  attribute destinationAerodrome: String; Destination aerodrome named in the flight plan.
  attribute estimatedElapsedTime: Duration; Elapsed time on the FPL used with ATOT to calculate ELDT (Milestone 3).
  attribute isRepetitive: Boolean; Whether a repetitive flight plan (RFPL) has been submitted covering daily or weekly flights (Milestone 1).

class AirportSlot (package Flights): The airport slot programme entry against which the ATC Flight Plan is checked for consistency.
  attribute slotReference: String; Reference identifying the coordinated slot the flight plan must correspond to (Milestone 1).

class TimeQuantity (package Timings): A named time quantity describing a flight's progress, combining a prefix (Scheduled, Estimated, Target, Actual, Calculated) with an event, kept as a history of successive values.
  attribute quantityName: String; The named quantity, e.g. TOBT, EOBT, ELDT, EIBT, ETOT, TTOT, CTOT, ATOT, ALDT, AIBT, ACGT, ASBT, ARDT, ASRT, ASAT, AOBT, SOBT.
  attribute event: EventType; The event this quantity describes, e.g. Off-Block, In-Block, Landing, Take-Off, Start-Up Approval.
  attribute value: DateTime; The current time value of this quantity.
  attribute originator: String; Who provided this value, e.g. ATC, AO/GH, ACARS, radar system.
  attribute accuracy: String; Stated accuracy, e.g. +/- 1 minute for actual times.
  attribute updatedAt: DateTime; Time this value was recorded.
  operation update(newValue: DateTime, originator: String): void; Appends a new successive value with its originator and time of update, rather than overwriting, so a turn-round can be analysed afterwards.

class ScheduledTime (package Timings): A scheduled-prefix time quantity such as SOBT.

class EstimatedTime (package Timings): An estimated-prefix time quantity such as EOBT, ELDT, EIBT, ETOT.

class TargetTime (package Timings): A target-prefix time quantity such as TOBT, TTOT, TSAT.

class ActualTime (package Timings): An actual-prefix time quantity such as ATOT, ALDT, AIBT, ACGT, ASBT, ARDT, ASRT, ASAT, AOBT.

class CalculatedTime (package Timings): A calculated-prefix time quantity such as CTOT.

class Milestone (package Milestones): One of the sixteen CDM events, each with its trigger, timing rule, effect on operational status, and procedure.
  attribute milestoneNumber: Integer; The milestone's number, 1 to 16.
  attribute milestoneName: String; The milestone's name, e.g. 'ATC Flight Plan Activated'.
  attribute definitionText: String; The definition of the milestone as stated in the document.
  attribute triggeredBy: String; What triggers this milestone's process, as stated under Procedures.
  attribute operationalStatusChange: FlightOperationalStatus; The operational status the flight changes to at this milestone.
  operation recordOccurrence(time: DateTime): void; Records that the milestone has occurred for a flight, at the stated time.

class FlightPlanActivation (package Milestones): Milestone 1: the ICAO flight plan is submitted to ATC and the Airport CDM Platform is initiated for the flight.
  operation checkConsistency(flightPlan: AtcFlightPlan, slot: AirportSlot, flight: Flight): Boolean; Checks consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
  operation updateEstimates(flight: Flight): void; Updates ELDT and EIBT for an arrival, and ETOT for a departure.
  operation sendFirstEdpi(flight: Flight): void; Sends the first E-DPI only if consistent information has been provided; not sent if information is missing or inconsistent.

class Eobt2HrCheck (package Milestones): Milestone 2: at EOBT-2hr, flights are known as regulated or not and receive a CTOT if regulated.
  operation checkFlightEstimatesConsistency(flight: Flight): Boolean; Checks whether AO/GH flight estimates are consistent with the ATC Flight Plan at EOBT-2hrs, before or after take-off from outstation.
  operation calculateTtot(flight: Flight): DateTime; Calculates TTOT taking into account EIBT+MTTT+EXOT if later than EOBT+EXOT; if TOBT is manually input it overrides, so TTOT equals TOBT+EXOT.
  operation markAsRegulated(flight: Flight): void; Marks appropriate fields as REGULATED for a flight receiving a CTOT.

class TakeOffFromOutstation (package Milestones): Milestone 3: the ATOT from the outstation (ADEP) is recorded.
  operation checkLandingEstimateConsistency(flight: Flight): Boolean; Checks whether AO/GH estimated landing time after take-off from outstation is consistent with the outbound ATC Flight Plan.
  operation calculateEldt(atot: DateTime, estimatedElapsedTime: Duration): DateTime; Calculates ELDT using ATOT and the Estimated Elapsed Time on the FPL.
  operation calculateTtot(flight: Flight): DateTime; Calculates TTOT as EIBT+MTTT+EXOT, or EOBT+EXOT if EOBT is later than EIBT+MTTT, or TOBT+EXOT if TOBT is available, respecting a TTOT tolerance of 5 minutes before informing Network Operations.

class LocalRadarUpdate (package Milestones): Milestone 4: the flight enters the FIR or local airspace of the destination airport.
  operation checkTobtConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT.
  operation computeEibt(eldt: DateTime, exit: Duration): DateTime; Computes EIBT using the ELDT and the estimated taxi-in time (EXIT).
  operation informNetworkOperationsIfTtotChanges(flight: Flight): void; Informs Network Operations when the TTOT changes by more than the agreed TTOT tolerance.

class FinalApproach (package Milestones): Milestone 5: the flight enters the Final Approach phase at the destination airport.
  operation checkTobtConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT.
  operation informNetworkOperationsIfTtotChanges(flight: Flight): void; Informs Network Operations when the TTOT changes by more than the agreed TTOT tolerance.

class Landed (package Milestones): Milestone 6: ALDT, the time an aircraft touches down on a runway.
  operation checkTobtConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation updateEibt(aldt: DateTime, exit: Duration): DateTime; Updates EIBT according to ALDT + EXIT.
  operation informNetworkOperationsIfTtotChanges(flight: Flight): void; Informs Network Operations when TTOT changes by more than the agreed TTOT tolerance.

class InBlock (package Milestones): Milestone 7: AIBT, the time an aircraft arrives in-blocks; ACGT is considered to commence at AIBT.
  operation checkTobtConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation updateTobtTtot(flight: Flight): void; Updates TOBT and TTOT, calculated on the basis of the estimated turn-round period for the departing flight.

class GroundHandlingStarted (package Milestones): Milestone 8: commencement of ground handling operations (ACGT), specific to first-of-day or long-parked flights.
  operation checkTobtConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation updateTobtTtot(flight: Flight): void; Updates TOBT, calculated on the basis of the estimated turn-round period for the departing flight.

class FinalConfirmationOfTobt (package Milestones): Milestone 9: the time the Aircraft Operator/Ground Handler provides its most accurate TOBT.
  attribute localParameterT: Duration; t minutes before EOBT, a parameter time agreed locally, when this confirmation is provided.
  operation checkTobtConsistency(flight: Flight): Boolean; Performed at a predefined local time to confirm TOBT prior to TSAT issue and verify feasibility of ATC Flight Plan estimates given the updated TOBT.
  operation calculateExot(trafficLoad: String, gateLocation: String, runwayInUse: String, holdingPeriod: Duration): Duration; ATC calculates and provides EXOT based on predicted traffic load, gate/stand location, runway in use, and waiting period at the Holding Position.

class TsatIssued (package Milestones): Milestone 10: the time ATC issues the Target Start-Up Approval Time.
  attribute localParameterT: Duration; t-minutes before EOBT, a parameter agreed locally, when TSAT is issued.
  attribute tobtUpdateThreshold: Integer; Locally defined tolerance for the number of TOBT updates permitted after TSAT has been issued.
  operation informPartnersOfTsat(flight: Flight): void; Informs all relevant partners of the TSAT allocated to the flight; Network Operations is informed by a T-DPI-s for non-regulated flights.
  operation checkTobtUpdateCount(flight: Flight): Boolean; Checks whether the number of TOBT updates after TSAT has been issued exceeds a locally defined tolerance.

class BoardingStarts (package Milestones): Milestone 11: the gate is open for passengers to physically start boarding.
  operation informPartnersOfAsbt(flight: Flight): void; Informs all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT).
  operation checkBoardingStatus(flight: Flight): Boolean; At a locally defined time before TOBT, checks whether boarding starts in time to respect TOBT and informs the AO/GH if TOBT needs updating.

class AircraftReady (package Milestones): Milestone 12: all doors closed, boarding bridge removed, push-back vehicle connected, ready to taxi (ARDT).
  operation informPartnersOfArdt(flight: Flight): void; Informs all relevant Airport CDM Partners of ARDT and that the aircraft is ready for start-up/push-back.
  operation alertIfNoReadyStatus(flight: Flight): void; At TOBT + tolerance, informs the AO/GH that TOBT has passed and no ARDT or Ready Status (RDY) has been received.

class StartUpRequested (package Milestones): Milestone 13: the time that start-up is requested (ASRT), based on pilot request.
  operation informPartnersOfAsrt(flight: Flight): void; Informs all relevant Airport CDM Partners of Actual Start-up Request Time (ASRT).
  operation alertIfNoStartUpRequested(flight: Flight): void; If start-up request is not made by TSAT + tolerance, informs the AO/GH that no start-up has been requested, who should update TOBT.

class StartUpApproved (package Milestones): Milestone 14: ASAT, the time an aircraft receives its start-up approval.
  operation informPartnersOfAsat(flight: Flight): void; Informs all relevant Airport CDM Partners of ASAT and that the aircraft has received start-up approval/push-back clearance.
  operation checkAsatAgainstTsat(flight: Flight): Boolean; Checks if ASAT is in accordance with TSAT; if start-up approval is not granted at TSAT + tolerance, all partners are informed and the flight is re-sequenced.

class OffBlock (package Milestones): Milestone 15: AOBT, the time the aircraft pushes back/vacates the parking position.
  operation informPartnersOfAobt(flight: Flight): void; Informs all relevant Airport CDM Partners of AOBT and that the aircraft has commenced push-back/taxi from parking position.
  operation checkTtotAgainstTolerance(flight: Flight): void; AOBT always triggers an A-DPI message; after the first A-DPI, checks TTOT updates against the TTOT tolerance before Network Operations is informed with a new A-DPI.

class TakeOff (package Milestones): Milestone 16: ATOT, the time an aircraft takes off from the runway.
  operation informPartnersOfAtot(flight: Flight): void; Informs all relevant Airport CDM Partners about the actual take-off.
  operation removeFromDepartureSequence(flight: Flight): void; An airborne message is generated and the flight is removed from the departure sequence.

class AirportCdmPlatform (package Systems): The Airport CDM Platform that is initiated for a flight, processes all available information, and performs ACISP actions.
  operation initiateForFlight(flight: Flight): void; Initiates the Airport CDM Platform for the flight and processes all available information (Milestone 1).
  operation markFieldsAsRegulated(flight: Flight): void; Marks appropriate fields as REGULATED (Milestone 2).
  operation computeTobtAutomatically(flight: Flight): DateTime; Calculates a new TOBT automatically following an update of ELDT (Milestone 4).
  operation receiveInput(flight: Flight, input: String): void; Receives an input to the Airport CDM Platform, triggering the Aircraft Ready procedure (Milestone 12).

class AtcSystem (package Systems): The ATC/radar/A-SMGCS system that detects a flight and provides actual times such as ATOT, ALDT and AIBT.
  attribute systemType: String; e.g. ACC, Approach Control Unit, A-SMGCS, Tower FDPS, Radar.
  operation detectFlight(ssrCode: String): void; Detects a flight based upon the assigned SSR code when it crosses a defined FIR/ATC boundary or range/position/level (Milestones 4,5).

class Acars (package Systems): The Aircraft Communications Addressing and Reporting System that signals ON/OFF/IN/OUT events.
  operation signalEvent(event: EventType): void; Signals ACARS=ON (landing), ACARS=IN (in-block), ACARS=OUT (off-block), or ACARS=OFF (take-off).

class Ifps (package Systems): The Integrated Initial Flight Plan Processing System that distributes the ATC Flight Plan to all involved ATC units.
  operation distributeFlightPlan(flightPlan: AtcFlightPlan): void; Distributes the ATC Flight Plan submitted by the Aircraft Operator to all involved ATC units including departure and destination aerodromes.

class Etfms (package Systems): The system Network Operations uses to monitor a flight's progress within 3 hours flying time of the destination airport.
  operation monitorProgress(flight: Flight): void; Monitors progress of the flight and triggers sending of a Flight Update Message (FUM) with updates of the flight's progress.

class DpiMessage (package Messages): A Departure Planning Information message exchanged with Network Operations as part of the DPI process.
  attribute sentTime: DateTime; When the message was sent.
  attribute sender: String; The party or system sending the message.

class EDpiMessage (package Messages): The first E-DPI message, sent only if consistent SOBT, aircraft registration and first destination data have been provided.

class TDpiMessage (package Messages): The T-DPI message informing Network Operations of the updated take-off time estimate at EOBT-2hr.

class TDpiTMessage (package Messages): The T-DPI-t message informing Network Operations of updated take-off time estimates at take-off from outstation.

class TDpiSMessage (package Messages): The T-DPI-s message informing Network Operations of the TSAT for non-regulated flights.

class ADpiMessage (package Messages): The A-DPI message that AOBT always triggers to Network Operations, and which carries updated TTOT thereafter.

class FumMessage (package Messages): The Flight Update Message sent by Network Operations providing updates of the flight's progress.

class FsaMessage (package Messages): The FSA message sent at Take-Off.

class MvtMessage (package Messages): The MVT message sent at Take-Off.

class ReadyStatusMessage (package Messages): The Ready Status (RDY) message confirming that the flight follows the indicated TOBT.
