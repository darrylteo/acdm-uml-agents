# The document: sixteen A-CDM milestones, sentences numbered

## Milestone 1: ATC Flight Plan Activated

### Definition

[M1.definition.1] The ICAO flight plan is submitted to ATC.
[M1.definition.2] The Airport CDM Platform is initiated for this flight, and all available information is processed.
### Origin and priority

[M1.origin_and_priority.1] The ATC Flight Plan is submitted by the Aircraft Operator and distributed by the IFPS.
[M1.origin_and_priority.2] All involved ATC units receive the flight plan, including departure and destination aerodromes.
### Timing

[M1.timing.1] Normally this takes place 3 hours before EOBT, however it may be later.
[M1.timing.2] In some cases a repetitive flight plan (RFPL) has been submitted, covering daily or weekly flights.
### Data Quality

[M1.data_quality.1] The ATC Flight Plan corresponds to the airport slot programme.
### Effect

[M1.effect.1] One aircraft turn-round normally includes an arriving and a departing flight, meaning that it will have two related flight plans.
[M1.effect.2] For coordinated airports, the outbound flight is already known.
[M1.effect.3] The flight plan may be used to update certain information such as type of aircraft.
[M1.effect.4] For long distance flights, the ELDT may differ from the airport slot.
[M1.effect.5] For non coordinated airports, the flight plan is used to initiate the outbound flight.
[M1.effect.6] The flight is ready not later than 15 minutes after the planned EOBT.
[M1.effect.7] The DPI process commences the correct messaging with Network Operations (if implemented - see attachment 2 for details).
### Procedures

[M1.procedures.1] To check consistency between ATC Flight Plan, Airport Slot and Airport flight data and then confirm the flight to the Network Operations and allow further local processing of the flight.
[M1.procedures.2] This check shall be performed to verify the consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
[M1.procedures.3] The AO must provide correct information before this first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible.
[M1.procedures.4] The E-DPI message should not be sent if no or inconsistent information is provided.
[M1.procedures.5] This process is triggered by:
[M1.procedures.6] - The first activation of the ATC Flight Plan (earliest EOBT-3 hr), or
[M1.procedures.7] - New or late submissions of the ATC Flight Plan, after cancellation or revised EOBT
### Operational Status (changes to)

[M1.operational_status.1] INITIATED
### Action on CDM Operation (ACISP)

[M1.action_on_cdm.1] ELDT and EIBT updated for an arrival EOBT and ETOT updated for a departure The DPI process commences (if implemented - see section 3.7.3 for details).
## Milestone 2: EOBT - 2 hr

### Definition

[M2.definition.1] At EOBT-2 hr most flights will be known in the Airport CDM Platform including if they are regulated or not.
[M2.definition.2] All regulated flights receive a CTOT from Network Operations.
### Origin and priority

[M2.origin_and_priority.1] The CTOT is issued by the Network Operations and is sent to relevant ATS units as well as the departure aerodrome.
[M2.origin_and_priority.2] CTOT flights usually have a priority over unregulated flights.
### Timing

[M2.timing.1] If the flight is regulated, a CTOT is issued at EOBT-2h.
### Data Quality

[M2.data_quality.1] Not applicable.
### Effect

[M2.effect.1] For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.
### Procedures

[M2.procedures.1] To check (before or after take off from outstation) whether AO/GH flight estimates are consistent with the ATC Flight Plan and to inform Network Operations about the updated take off time estimate, using a T-DPI Message.
[M2.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs.
[M2.procedures.3] At EOBT-2 hrs Network Operations is informed through the first T-DPI message.
[M2.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT.
[M2.procedures.5] In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M2.procedures.6] This procedure is triggered by
[M2.procedures.7] - a time stamp, at EOBT - 2h.
### Operational Status (changes to)

[M2.operational_status.1] N. A.
### Action on CDM Operation (ACISP)

[M2.action_on_cdm.1] ETOT/TTOT/CTOT Mark appropriate fields as REGULATED
## Milestone 3: Take Off from Outstation

### Definition

[M3.definition.1] The ATOT from the outstation (ADEP)
### Origin and priority

[M3.origin_and_priority.1] The outstation provides ATOT to the Network Operations and Aircraft Operator.
### Timing

[M3.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M3.data_quality.1] The accuracy of ATOT is +/- 1 minute.
### Effect

[M3.effect.1] If the departure airport is more than 3hrs flying time from the destination airport the ATOT is received from either the Network Operations FUM or via the Aircraft Operator / Ground Handler.
[M3.effect.2] Using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
[M3.effect.3] If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS and send a Flight Update Message (FUM) that provides updates of the flight's progress.
### Procedures

[M3.procedures.1] To check whether the AO/GH estimated landing time after take off from outstation are consistent with the outbound ATC Flight Plan, and when needed inform the Network Operations about the updated take off time estimates using a T-DPI-t Message.
[M3.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation.
[M3.procedures.3] A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT.
[M3.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT.
[M3.procedures.5] In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT.
[M3.procedures.6] In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M3.procedures.7] This process is triggered by
[M3.procedures.8] - the take off from outstation.
### Operational Status (changes to)

[M3.operational_status.1] AIRBORNE
### Action on CDM Operation (ACISP)

[M3.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 4: Local Radar Update

### Definition

[M4.definition.1] The flight enters the FIR (Flight Information Region) or the local airspace of the destination airport.
### Origin and priority

[M4.origin_and_priority.1] This information is normally available from the Area Control Centre (ACC) or Approach Control Unit that is associated with an airport.
[M4.origin_and_priority.2] The radar system is able to detect a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
### Timing

[M4.timing.1] Dependent upon the position of the airport in relation to the FIR boundary.
### Data Quality

[M4.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M4.effect.1] Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.
[M4.effect.2] The accuracy of ELDT is particularly important at this stage since downstream decisions are taken, such as stand /gate / aircraft changes, preparation of arrival sequence, preparation of ground handling operations, decisions for connecting passengers.
[M4.effect.3] Uncertainty and ELDT non-accuracy at this stage significantly increase risks for bad and last minute decisions and internal disruptions.
[M4.effect.4] The objective to decrease the number of stand and gate changes in the last 30 minutes requires high accuracy regarding departure and arrival times.
[M4.effect.5] Therefore, taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.
[M4.effect.6] The update of TOBT for the related departing flight takes place following this milestone.
[M4.effect.7] Decisions such as the turn-round period, connecting passengers etc are taken and need to be stable at this event.
[M4.effect.8] An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
### Procedures

[M4.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M4.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M4.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M4.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M4.procedures.5] This process is triggered by
[M4.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M4.operational_status.1] FIR
### Action on CDM Operation (ACISP)

[M4.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 5: Final Approach

### Definition

[M5.definition.1] The flight enters the Final Approach phase at the destination airport.
### Origin and priority

[M5.origin_and_priority.1] This information is normally available from ATC.
[M5.origin_and_priority.2] The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range / position or passes/leaves a predetermined level.
### Timing

[M5.timing.1] Dependent upon local parameters that are defined by ATC.
### Data Quality

[M5.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M5.effect.1] Update of the ELDT to determine a new TOBT.
[M5.effect.2] When a flight reaches this stage it is usually between 2 and 5 minutes from landing (depending on the parameter set by ATC).
[M5.effect.3] This is often the prompt for many partners to start moving resources connected with the flight, such as positioning a parking marshal and ground handling services.
### Procedures

[M5.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M5.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M5.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M5.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M5.procedures.5] This process is triggered by
[M5.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M5.operational_status.1] FINAL
### Action on CDM Operation (ACISP)

[M5.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 6: Landed

### Definition

[M6.definition.1] ALDT - Actual Landing Time.
[M6.definition.2] This is the time that an aircraft touches down on a runway.
[M6.definition.3] (Equivalent to ATC ATA - Actual Time of Arrival landing, ACARS=ON).
### Origin and priority

[M6.origin_and_priority.1] Provided by ATC system or by ACARS from equipped aircraft.
### Timing

[M6.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M6.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M6.effect.1] The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator / Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
[M6.effect.2] The EIBT can be updated according to the ALDT +EXIT.
### Procedures

[M6.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M6.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M6.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
[M6.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M6.procedures.5] This process is triggered by
[M6.procedures.6] - Actual Landing Time: ALDT
### Operational Status (changes to)

[M6.operational_status.1] LANDED
### Action on CDM Operation (ACISP)

[M6.action_on_cdm.1] ELDT changes to ALDT, EIBT, TOBT and TTOT updated

## Milestone 9: Final Confirmation of the TOBT

### Definition

[M9.definition.1] The time at which the Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.
### Origin and priority

[M9.origin_and_priority.1] The Aircraft Operator / Ground Handler provides the information.
### Timing

[M9.timing.1] The information is provided t minutes before EOBT (t is a parameter time agreed locally).
### Data Quality

[M9.data_quality.1] Accuracy is agreed locally.
### Effect

[M9.effect.1] The aim of the final TOBT is to give a timely, accurate and reliable assessment of the off-block time.
[M9.effect.2] It is recognised that main benefits of sharing the TOBT are expected in case of disruptions (internal or external).
[M9.effect.3] In such cases, the difference between EOBT (shared by ATC, Network Operations and Stand / Gate Management) and TOBT may be important.
[M9.effect.4] An accurate TOBT at [EOBT-t minutes] is a pre-requisite for ATC to establish a push back / pre-departure sequence.
[M9.effect.5] Emphasis is put on the need for the Aircraft Operator to integrate his own strategy to compute a TOBT related to the flight.
[M9.effect.6] Following the receipt of the TOBT, the ATC system will calculate and provide the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate / stand location, runway in use, and waiting period at the Holding Position, etc. The flight is introduced into the pre-departure sequence.
[M9.effect.7] The Aircraft Operator / Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M9.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M9.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M9.procedures.3] This check should be performed at a predefined time (local parameter) to confirm TOBT prior to TSAT issue and verify feasibility of the ATC Flight Plan estimates given the updated TOBT.
[M9.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M9.procedures.5] This Milestone Process is actually constantly applicable in the CDM Platform, as soon as a TOBT is available.
[M9.procedures.6] However the confirmed TOBT prior to TSAT has special status, where AO/GH check the quality of TOBT before TSAT issue.
### Operational Status (changes to)

[M9.operational_status.1] IN-BLOCK
### Action on CDM Operation (ACISP)

[M9.action_on_cdm.1] This process is triggered by - a new TOBT or TTOT update.
[M9.action_on_cdm.2] No need to confirm an existing TOBT if it has been manually modified before.

### Definition

[M10.definition.1] The time ATC issues the Target Start Up Approval Time
### Origin and priority

[M10.origin_and_priority.1] ATC
### Timing

[M10.timing.1] The information is provided t-minutes before EOBT, where t is a parameter agreed locally
### Data Quality

[M10.data_quality.1] Accuracy is agreed locally.
### Effect

[M10.effect.1] The flight is stabilised into the pre-departure sequence.
[M10.effect.2] The Aircraft Operator/ Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M10.procedures.1] First step: To inform all relevant partners of the TSAT that has been allocated to the flight.
[M10.procedures.2] The Network Operations is informed by a T-DPI-s for non regulated flights.
[M10.procedures.3] Second step: To check whether the number of TOBT updates exceeds a tolerance defined locally, after TSAT has been issued.
[M10.procedures.4] First: The TSAT will indicate to the partners the time when the start up approval can be expected.
[M10.procedures.5] Network Operations will be informed with a T-DPI-s for non regulated flights.
[M10.procedures.6] No check is performed.
[M10.procedures.7] Second: A check shall be performed to see the number of TOBT updates after TSAT has been issued.
[M10.procedures.8] In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.
[M10.procedures.9] This process is triggered by
[M10.procedures.10] - A defined time (local parameter) before TOBT
[M10.procedures.11] - TOBT update after TSAT issue

[M11.definition.2] This is not to be confused with the time passengers are pre-called to the gate via flight information display systems (FIDS) or public address systems.
### Origin and priority

[M11.origin_and_priority.1] Automatic from airport system or manual input by Aircraft Operator/ Ground Handler.
### Timing

[M11.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M11.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M11.effect.1] When boarding commences it gives the Airport CDM Partners a good indication of whether the TOBT/TSAT will be respected.
### Procedures

[M11.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT).
[M11.procedures.2] Second step: To check whether boarding starts in time to respect TOBT and inform the AO/GH in case TOBT needs to be updated.
[M11.procedures.3] Inform of Actual Start Boarding Time (ASBT) when it occurs.
[M11.procedures.4] At a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status.
[M11.procedures.5] This process is triggered by
[M11.procedures.6] - a time variable <value> minutes before TOBT.
### Operational Status (changes to)

## Milestone 12: Aircraft Ready

### Definition

[M12.definition.1] The time when all doors are closed, boarding bridge removed, push back vehicle connected, ready to taxi immediately upon reception of TWR instructions (ARDT).
### Origin and priority

[M12.origin_and_priority.1] Provided by the Aircraft Operator/ Ground Handler.
### Timing

[M12.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M12.data_quality.1] Data is directly available with an accuracy of +/- 1 minute.
### Effect

[M12.effect.1] ATC refines the pre-departure sequence.
[M12.effect.2] The pilot requests start up just before TSAT, following coordination with the Ground Handler.
[M12.effect.3] (Dispatcher / Supervisor / Redcap).
### Procedures

[M12.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up / push-back.
[M12.procedures.2] Second step: To inform the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).
[M12.procedures.3] Inform of ARDT or RDY confirming that the flight follows the indicated TOBT.
[M12.procedures.4] At TOBT + tolerance the AO/GH are informed that TOBT has passed and there has not been a ready status message yet.
[M12.procedures.5] This procedure is triggered by
[M12.procedures.6] - an input to the Airport CDM Platform.

## Milestone 15: Off-Block

### Definition

[M15.definition.1] AOBT - Actual Off-Block Time.
[M15.definition.2] The time the aircraft pushes back/vacates the parking position (Equivalent to Airline/Handler ATD - Actual Time of Departure ACARS=OUT).
### Origin and priority

[M15.origin_and_priority.1] ACARS equipped aircraft or automated docking systems or ATC systems (e.g. A-SMGCS) or by manual input.
### Timing

[M15.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M15.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M15.effect.1] TTOT updated considering the EXOT.
### Procedures

[M15.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back / taxi from parking position.
[M15.procedures.2] Second step: To check if TTOT changes by more than the agreed tolerance and inform Network Operations.
[M15.procedures.3] Inform of AOBT when it occurs.
[M15.procedures.4] AOBT always triggers an A-DPI message to Network Operations or in the case of remote holding at a defined time prior to TTOT.
[M15.procedures.5] After a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.
[M15.procedures.6] This process is triggered by AOBT detection.

[M15.operational_status.1] OFF-BLOCK

## Milestone 16: Take Off

### Definition

[M16.definition.1] ATOT - Actual Take Off Time.
[M16.definition.2] This is the time that an aircraft takes off from the runway.
[M16.definition.3] (Equivalent to ATC ATD-Actual Time of Departure, ACARS = OFF).
### Origin and priority

[M16.origin_and_priority.1] Provided by ATC system or from ACARS equipped aircraft.
### Timing

[M16.timing.1] The information is directly available as soon as possible after occurrence of the milestone.
### Data Quality

[M16.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M16.effect.1] FSA and MVT messages are sent.
### Procedures

[M16.procedures.1] To inform all relevant Airport CDM Partners about the actual take off.
[M16.procedures.2] An airborne message is generated and the flight is removed from the departure sequence.
[M16.procedures.3] This process is triggered by Tower FDPS, A-SMGCS / Radar detection or ACARS.
### Operational Status (changes to)

[M16.operational_status.1] DEPARTED / TAKE OFF
### Action on CDM Operation (ACISP)

[M16.action_on_cdm.1] ATOT recorded

# The model

class AirportCdmPartner (package Stakeholders): A generic party in the Airport CDM process that originates or receives flight information and notifications.

class AircraftOperator (package Stakeholders): The airline or its representative that submits the ATC Flight Plan and provides TOBT and other flight estimates.
  operation provideFlightData(sobt: DateTime, aircraftRegistration: String, firstDestination: String): void; The AO must provide correct information before the first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible.

class GroundHandler (package Stakeholders): The party that performs and reports ground handling operations and turn-round estimates on behalf of the aircraft operator.

class AirTrafficControlUnit (package Stakeholders): An air traffic control body, including the tower, Area Control Centre, and Approach Control Unit, that manages the flight's sequencing and clearances.

class NetworkOperations (package Stakeholders): The network management party that issues CTOT, monitors flight progress via ETFMS/FUM, and receives DPI messages.
  operation issueCtot(flight: Flight): TakeOffTime; The Network Operations issues the CTOT and sends it to relevant ATS units as well as the departure aerodrome. If the flight is regulated, a CTOT is issued at EOBT-2h.
  operation monitorFlightProgress(flight: Flight): void; If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS and sends a Flight Update Message (FUM) that provides updates of the flight's progress.

class Ifps (package Stakeholders): The Integrated Initial Flight Plan Processing System party that distributes the submitted ATC Flight Plan to involved ATC units.

class FlightCrew (package Stakeholders): The pilot and crew who request start-up approval and coordinate the turn-round with the ground handler.

class StandGateManagement (package Stakeholders): The party responsible for stand and gate allocation that shares EOBT information and is affected by stand/gate change decisions.

class Flight (package Flights): A single scheduled arrival or departure operation of an aircraft, tracked through the sixteen milestones with its operational status and time quantities.
  attribute operationalStatus: FlightOperationalStatus; The current operational status of the flight, updated at each milestone (e.g. INITIATED, AIRBORNE, LANDED, OFF-BLOCK).
  attribute ssrCode: String; The SSR transponder code assigned to the flight, used by radar systems to detect it crossing the FIR/TMA boundary or entering final approach (milestones 4, 5).

class TurnRound (package Flights): The aircraft turn-round linking an arriving flight and its related departing flight so that ground handling and estimates can be analysed together.

class Aircraft (package Flights): The physical aircraft operating a flight, identified by type and registration, which may be updated from the flight plan.
  attribute registration: String; The aircraft registration, provided by the Aircraft Operator before the first E-DPI message is sent (milestone 1).
  attribute type: String; The type of aircraft, which may be updated from information in the ATC Flight Plan (milestone 1).

class FlightPlan (package Flights): The ICAO/ATC Flight Plan submitted by the Aircraft Operator, possibly a repetitive flight plan, describing departure and destination aerodromes and other flight data.
  attribute departureAerodrome: String; The departure aerodrome named in the ATC Flight Plan, distributed by the IFPS to all involved ATC units (milestone 1).
  attribute destinationAerodrome: String; The destination aerodrome named in the ATC Flight Plan, distributed by the IFPS to all involved ATC units (milestone 1).
  attribute isRepetitive: Boolean; Whether the flight plan is a repetitive flight plan (RFPL) covering daily or weekly flights (milestone 1).

class AirportSlot (package Flights): The airport slot programme entry against which the ATC Flight Plan's consistency is checked.
  attribute slotTime: DateTime; The scheduled time held in the airport slot programme, against which the ATC Flight Plan's consistency is checked (milestone 1).

class TimeQuantity (package Timings): A general time value describing a flight's progress toward or through a milestone event, carrying its prefix, origin, accuracy, and successive updates.
  attribute value: DateTime; The date and time value of this time quantity.
  attribute prefix: TimeQuantityPrefix; Which prefix category (Scheduled, Estimated, Target, Actual, Calculated) this value represents.
  attribute originator: AirportCdmPartner; The stakeholder or system that provided or last updated this value.
  attribute recordedAt: DateTime; The time this value was recorded; successive values are appended rather than overwriting earlier ones so the turn-round can be analysed afterwards.
  attribute accuracy: Duration; The stated accuracy of this time value where given in the document, e.g. ±1 minute for actual times available directly after occurrence of a milestone.

class OffBlockTime (package Timings): The scheduled, estimated, target, or actual time an aircraft leaves its parking position (SOBT, EOBT, TOBT, AOBT).

class LandingTime (package Timings): The estimated or actual time an aircraft touches down (ELDT, ALDT).

class InBlockTime (package Timings): The estimated or actual time an aircraft arrives in-blocks (EIBT, AIBT).

class TakeOffTime (package Timings): The estimated, target, calculated, or actual time an aircraft takes off (ETOT, TTOT, CTOT, ATOT).

class StartUpApprovalTime (package Timings): The target or actual time an aircraft receives start-up approval (TSAT, ASAT).

class StartUpRequestTime (package Timings): The actual time start-up is requested by the flight crew (ASRT).

class ReadyTime (package Timings): The actual time an aircraft is ready for start-up and push-back, with all doors closed and equipment removed (ARDT).

class BoardingTime (package Timings): The actual time passengers start boarding the aircraft (ASBT).

class GroundHandlingTime (package Timings): The actual time ground handling operations commence for a flight (ACGT).

class TaxiOutTime (package Timings): The estimated taxi-out time between off-block and take-off, calculated by ATC based on traffic load, stand location, and runway in use (EXOT).
  attribute duration: Duration; The estimated taxi-out time (EXOT) between off-block and take-off, calculated by the ATC system based on predicted traffic load, gate/stand location, runway in use, and waiting period at the Holding Position (milestone 9).

class TaxiInTime (package Timings): The estimated taxi-in time between landing and in-block used to compute EIBT (EXIT).
  attribute duration: Duration; The estimated taxi-in time (EXIT) from landing to in-block, used together with ELDT or ALDT to compute EIBT (milestones 4, 6).

class TurnRoundTime (package Timings): The minimum or estimated turn-round period used to calculate the departing flight's TOBT (MTTT, ETTT).
  attribute duration: Duration; The minimum or estimated turn-round period (MTTT/ETTT) used to calculate the departing flight's TOBT (milestones 2, 3, 6, 7, 8).

class FlightPlanActivation (package Milestones): Milestone 1: processes the activated ATC Flight Plan, checks its consistency with the Airport Slot and airport flight data, and confirms the flight for further processing.
  attribute activationOffset: Duration; The normal offset before EOBT at which the ATC Flight Plan is activated, EOBT-3 hours, though activation may occur later (milestone 1).
  attribute readinessOffset: Duration; The maximum offset after the planned EOBT by which the flight must be ready, 15 minutes (milestone 1).
  operation checkConsistency(flightPlan: FlightPlan, airportSlot: AirportSlot, flight: Flight): Boolean; Checks consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent, and then confirms the flight to the Network Operations and allows further local processing of the flight.
  operation activate(flightPlan: FlightPlan): void; Triggered by the first activation of the ATC Flight Plan (earliest EOBT-3 hr), or by new or late submissions of the ATC Flight Plan, after cancellation or revised EOBT.
  operation updateTimingsOnActivation(flight: Flight): void; For an arrival, ELDT and EIBT are updated; for a departure, EOBT and ETOT are updated.
  operation checkFlightReady(flight: Flight, plannedEobt: DateTime): Boolean; The flight is ready not later than 15 minutes after the planned EOBT.

class EobtMinus2Hours (package Milestones): Milestone 2: checks flight estimates against the ATC Flight Plan at EOBT-2 hours, issues CTOT for regulated flights, and informs Network Operations via the first T-DPI message.
  attribute ctotIssuanceOffset: Duration; The fixed offset before EOBT, 2 hours, at which a regulated flight is issued its CTOT (milestone 2).
  operation checkEstimatesConsistency(flight: Flight): Boolean; Checks (before or after take off from outstation) whether AO/GH flight estimates are consistent with the ATC Flight Plan and informs Network Operations about the updated take off time estimate, using a T-DPI Message; this check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs.
  operation informFirstTdpi(flight: Flight): void; At EOBT-2 hrs Network Operations is informed through the first T-DPI message.
  operation calculateTtot(eibt: DateTime, mttt: Duration, exot: Duration, eobt: DateTime, tobt: DateTime): DateTime; Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT. In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
  operation updateInboundEldt(flight: Flight, fum: FlightUpdateMessage): void; For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.

class TakeOffFromOutstation (package Milestones): Milestone 3: on take off from the outstation, checks AO/GH landing estimates against the outbound flight plan and informs Network Operations of updated take-off time estimates via a T-DPI-t message.
  attribute ttotTolerance: Duration; The TTOT tolerance of 5 minutes respected before Network Operations is informed of the updated TTOT (milestone 3).
  attribute flyingTimeThreshold: Duration; The 3-hour flying-time threshold distinguishing whether ATOT-based ELDT calculation or FUM-based ETFMS progress monitoring is used (milestone 3).
  operation calculateEldt(atot: DateTime, estimatedElapsedTime: Duration): DateTime; Using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
  operation checkLandingEstimateConsistency(flight: Flight): Boolean; Checks whether the AO/GH estimated landing time after take off from outstation are consistent with the outbound ATC Flight Plan, and when needed informs the Network Operations about the updated take off time estimates using a T-DPI-t Message; this check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation. A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT.
  operation calculateTtot(eibt: DateTime, mttt: Duration, exot: Duration, eobt: DateTime, tobt: DateTime): DateTime; Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT. In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT. In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.

class TobtFeasibilityCheckMilestone (package Milestones): A common superclass for the milestone processes (radar update, final approach, landed, in-block, ground handling started, final TOBT confirmation) that check the AO/GH TOBT against the ATC Flight Plan and inform Network Operations when TTOT changes beyond the agreed tolerance.
  attribute ttotTolerance: Duration; The agreed TTOT tolerance respected before Network Operations is informed of an updated TTOT (milestones 4, 5, 6, 7, 8, 9).
  operation checkTobtConsistency(flight: Flight): Boolean; Checks whether the AO/GH TOBT is consistent with the ATC Flight Plan; performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
  operation informNetworkOperationsIfTtotChanged(flight: Flight): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance; the TTOT tolerance is respected before Network Operations is informed of updated TTOT.

class LocalRadarUpdate (package Milestones): Milestone 4: on radar detection at the FIR boundary, commences the TOBT process and updates ELDT/EIBT/TOBT/TTOT.
  attribute standGateChangeCutoff: Duration; The cutoff of ELDT-30 minutes, taking into account taxi-in time, after which a change to a stand or gate is not preferred (milestone 4).
  operation commenceTobtProcess(flight: Flight): void; Commences the TOBT process and checks whether the AO/GH TOBT is consistent with the ATC Flight Plan.
  operation calculateEibt(eldt: DateTime, exit: Duration): DateTime; An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
  operation checkStandGateChangeAllowed(eldt: DateTime, exit: Duration, now: DateTime): Boolean; Taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.

class FinalApproach (package Milestones): Milestone 5: on entering final approach, commences the TOBT process and updates ELDT-based estimates.
  attribute finalApproachWindow: Duration; The typical 2 to 5 minute window from landing at which a flight reaches final approach, depending on the ATC-defined parameter (milestone 5).
  operation commenceTobtProcess(flight: Flight): void; Commences the TOBT process and checks whether the AO/GH TOBT is consistent with the ATC Flight Plan.

class Landed (package Milestones): Milestone 6: on actual landing (ALDT), updates TOBT, TTOT and EIBT.
  operation updateDownstreamEstimates(flight: Flight): void; The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator/Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
  operation calculateEibt(aldt: DateTime, exit: Duration): DateTime; The EIBT can be updated according to the ALDT+EXIT.

class InBlock (package Milestones): Milestone 7: on actual in-block (AIBT), updates TOBT and TTOT based on the estimated turn-round period.
  operation updateDownstreamEstimates(flight: Flight): void; The occurrence of AIBT should trigger an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator/Ground Handler, calculated on the basis of the estimated turn-round period for the departing flight.

class GroundHandlingStarted (package Milestones): Milestone 8: on commencement of ground handling (ACGT), updates TOBT/TTOT based on the estimated turn-round period.
  operation updateTobt(flight: Flight): void; The occurrence of ACGT triggers an update of downstream estimates: TOBT is updated automatically or inserted manually by the Aircraft Operator/Ground Handler, calculated on the basis of the estimated turn-round period for the departing flight.

class FinalConfirmationOfTobt (package Milestones): Milestone 9: at a locally agreed time before EOBT, confirms the AO/GH's most accurate TOBT and triggers ATC calculation of EXOT.
  attribute confirmationOffset: Duration; The locally agreed parameter t, in minutes before EOBT, at which the AO/GH provides its most accurate final TOBT (milestone 9).
  operation confirmTobt(flight: Flight, tobt: DateTime): void; The Aircraft Operator/Ground Handler provides their most accurate TOBT taking into account the operational situation, t minutes before EOBT (t is a parameter time agreed locally).
  operation introduceToPreDepartureSequence(flight: Flight): void; The flight is introduced into the pre-departure sequence.
  operation needsConfirmation(tobt: DateTime): Boolean; This process is triggered by a new TOBT or TTOT update. There is no need to confirm an existing TOBT if it has been manually modified before.

class TsatIssued (package Milestones): Milestone 10: informs partners of the allocated TSAT via T-DPI-s and checks whether the number of TOBT updates after TSAT exceeds a locally defined tolerance.
  attribute issuanceOffset: Duration; The locally agreed parameter t, in minutes before EOBT/TOBT, at which TSAT is issued (milestone 10).
  attribute tobtUpdateThreshold: Integer; The locally defined tolerance on the number of TOBT updates permitted after TSAT has been issued, beyond which the TOBT input is processed per local procedure (milestone 10).
  operation informTsat(flight: Flight, tsat: DateTime): void; ATC informs all relevant partners of the TSAT that has been allocated to the flight. The Network Operations is informed by a T-DPI-s for non regulated flights.
  operation checkTobtUpdateCount(flight: Flight): Boolean; Checks whether the number of TOBT updates exceeds a tolerance defined locally, after TSAT has been issued. In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.

class BoardingStarts (package Milestones): Milestone 11: informs partners of Actual Start Boarding Time and checks whether boarding starts in time to respect TOBT.
  attribute boardingCheckOffset: Duration; A locally defined time variable, in minutes before TOBT (e.g. corresponding to aircraft type), at which the boarding status is checked (milestone 11).
  operation informAsbt(flight: Flight, asbt: DateTime): void; Informs all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT) when it occurs.
  operation checkBoardingStatus(flight: Flight): Boolean; Checks whether boarding starts in time to respect TOBT and informs the AO/GH in case TOBT needs to be updated; at a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status.

class AircraftReady (package Milestones): Milestone 12: informs partners of Actual Ready Time and alerts the AO/GH if TOBT has passed without a ready status being received.
  attribute readyTolerance: Duration; The tolerance added to TOBT after which the AO/GH is informed that no ARDT or Ready Status has yet been received (milestone 12).
  operation informArdt(flight: Flight, ardt: DateTime): void; Informs all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up/push-back.
  operation checkReadyStatusReceived(flight: Flight): Boolean; Informs the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY); at TOBT + tolerance the AO/GH are informed that TOBT has passed and there has not been a ready status message yet.

class StartUpRequested (package Milestones): Milestone 13: informs partners of Actual Start-up Request Time and alerts partners if no start-up request is made within the TSAT tolerance window.
  attribute tsatTolerance: Duration; The locally agreed TSAT tolerance window within which start-up must be requested, after which the AO/GH is alerted that no start-up has been requested (milestone 13).
  operation informAsrt(flight: Flight, asrt: DateTime): void; Informs all relevant Airport CDM Partners of Actual Start up Request Time (ASRT) in the Airport CDM Platform when it occurs.
  operation checkStartUpRequested(flight: Flight): Boolean; Alerts all relevant Airport CDM Partners when no start up has been requested inside the locally agreed TSAT tolerance window; if the start up request is not made by TSAT + tolerance, the AO/GH is informed that no start up has been requested, and should update TOBT.

class StartUpApproved (package Milestones): Milestone 14: informs partners of Actual Start-up Approval Time and checks that it accords with TSAT, alerting partners and re-sequencing the flight if not granted in time.
  attribute tsatTolerance: Duration; The tolerance added to TSAT by which start-up approval must be granted, after which all relevant partners are informed and the flight is re-sequenced (milestone 14).
  operation informAsat(flight: Flight, asat: DateTime): void; Informs all relevant Airport CDM Partners of Actual start up approval Time (ASAT) in the Airport CDM Platform and that the aircraft has received start up approval/push-back clearance when it occurs.
  operation checkAsatAgainstTsat(flight: Flight): Boolean; Checks if ASAT is in accordance with TSAT and alerts all relevant Airport CDM Partners when no start up has been granted; in case the start up approval is not granted at TSAT + tolerance, all relevant partners should be informed and the flight will be re-sequenced.

class OffBlock (package Milestones): Milestone 15: informs partners of Actual Off-Block Time, triggers an A-DPI message, and checks TTOT changes against tolerance before informing Network Operations.
  attribute ttotTolerance: Duration; The agreed tolerance checked against TTOT changes before Network Operations is informed with a new A-DPI (milestone 15).
  operation informAobt(flight: Flight, aobt: DateTime): void; Informs all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back/taxi from parking position when it occurs. AOBT always triggers an A-DPI message to Network Operations, or in the case of remote holding at a defined time prior to TTOT.
  operation checkTtotChange(flight: Flight): Boolean; Checks if TTOT changes by more than the agreed tolerance and informs Network Operations; after a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.
  operation calculateTtot(aobt: DateTime, exot: Duration): DateTime; TTOT updated considering the EXOT.

class TakeOff (package Milestones): Milestone 16: informs partners of the actual take-off, sends FSA and MVT messages, and removes the flight from the departure sequence.
  operation informTakeOff(flight: Flight, atot: DateTime): void; Informs all relevant Airport CDM Partners about the actual take off. An airborne message is generated and the flight is removed from the departure sequence.
  operation sendFsaAndMvtMessages(flight: Flight): void; FSA and MVT messages are sent.

class AirportCdmPlatform (package Systems): The central Airport CDM system that holds flight information, performs consistency checks, computes and updates time estimates, and triggers notifications throughout the process.
  operation markRegulated(flight: Flight): void; Marks appropriate fields as REGULATED and updates ETOT/TTOT/CTOT.
  operation calculateTobtFromEldt(flight: Flight, eldt: LandingTime): DateTime; Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.

class DpiProcess (package Systems): The process that commences correct DPI messaging with Network Operations when implemented.
  operation commenceMessaging(flight: Flight): void; The DPI process commences the correct messaging with Network Operations (if implemented).
  operation canSendEDpi(flightPlan: FlightPlan): Boolean; The E-DPI message should not be sent if no or inconsistent information is provided.

class EtfmsSystem (package Systems): The Enhanced Tactical Flow Management System used by Network Operations to monitor flight progress and generate Flight Update Messages.

class AtcSystem (package Systems): The ATC ground system that calculates the Estimated Taxi-Out Time based on traffic load, stand/gate location, runway in use, and holding position wait.
  operation calculateExot(flight: Flight): Duration; Following the receipt of the TOBT, the ATC system calculates and provides the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate/stand location, runway in use, and waiting period at the Holding Position, etc.

class SurveillanceSystem (package Systems): A radar, A-SMGCS, or Tower FDPS detection system that identifies a flight's position by SSR code to trigger milestone events.
  operation detectFlightAtFirBoundary(ssrCode: String): Boolean; The radar system detects a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
  operation detectFinalApproach(ssrCode: String): Boolean; The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range/position or passes/leaves a predetermined level.

class AcarsSystem (package Systems): The aircraft's ACARS reporting system that provides landing, in-block, off-block, and take-off events directly from the aircraft.

class FidsSystem (package Systems): The flight information display and public address system used to pre-call passengers, distinct from the physical start of boarding.

class DpiMessage (package Messages): A Departure Planning Information message (E-DPI, T-DPI, T-DPI-t, T-DPI-s, or A-DPI) sent to Network Operations to convey flight time estimates.
  attribute messageType: DpiMessageType; The type of DPI message sent to Network Operations (E-DPI, T-DPI, T-DPI-t, T-DPI-s, or A-DPI).

class FlightUpdateMessage (package Messages): The FUM sent by Network Operations providing updates of an inbound flight's progress toward the destination.

class ReadyStatusMessage (package Messages): The RDY message confirming that an aircraft is ready for start-up and push-back.

class DepartureClearanceMessage (package Messages): The voice or DCL message by which flight crew request start-up approval.

class FlightStatusMessage (package Messages): The FSA message sent on actual take-off to inform relevant systems of the flight's status.

class MovementMessage (package Messages): The MVT message sent on actual take-off reporting the aircraft's movement.

class AirborneMessage (package Messages): The message generated on take-off confirming the flight is airborne and removing it from the departure sequence.
