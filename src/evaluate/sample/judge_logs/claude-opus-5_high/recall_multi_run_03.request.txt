# The document: sixteen A-CDM milestones, sentences numbered

## Milestone 1: ATC Flight Plan Activated

### Definition

[M1.definition.1] The ICAO flight plan is submitted to ATC.
[M1.definition.2] The Airport CDM Platform is initiated for this flight, and all available information is processed.
### Origin and priority

[M1.origin_and_priority.1] The ATC Flight Plan is submitted by the Aircraft Operator and distributed by the IFPS.
[M1.origin_and_priority.2] All involved ATC units receive the flight plan, including departure and destination aerodromes.
### Timing

[M1.timing.1] Normally this takes place 3 hours before EOBT, however it may be later.
[M1.timing.2] In some cases a repetitive flight plan (RFPL) has been submitted, covering daily or weekly flights.
### Data Quality

[M1.data_quality.1] The ATC Flight Plan corresponds to the airport slot programme.
### Effect

[M1.effect.1] One aircraft turn-round normally includes an arriving and a departing flight, meaning that it will have two related flight plans.
[M1.effect.2] For coordinated airports, the outbound flight is already known.
[M1.effect.3] The flight plan may be used to update certain information such as type of aircraft.
[M1.effect.4] For long distance flights, the ELDT may differ from the airport slot.
[M1.effect.5] For non coordinated airports, the flight plan is used to initiate the outbound flight.
[M1.effect.6] The flight is ready not later than 15 minutes after the planned EOBT.
[M1.effect.7] The DPI process commences the correct messaging with Network Operations (if implemented - see attachment 2 for details).
### Procedures

[M1.procedures.1] To check consistency between ATC Flight Plan, Airport Slot and Airport flight data and then confirm the flight to the Network Operations and allow further local processing of the flight.
[M1.procedures.2] This check shall be performed to verify the consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
[M1.procedures.3] The AO must provide correct information before this first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible.
[M1.procedures.4] The E-DPI message should not be sent if no or inconsistent information is provided.
[M1.procedures.5] This process is triggered by:
[M1.procedures.6] - The first activation of the ATC Flight Plan (earliest EOBT-3 hr), or
[M1.procedures.7] - New or late submissions of the ATC Flight Plan, after cancellation or revised EOBT
### Operational Status (changes to)

[M1.operational_status.1] INITIATED
### Action on CDM Operation (ACISP)

[M1.action_on_cdm.1] ELDT and EIBT updated for an arrival EOBT and ETOT updated for a departure The DPI process commences (if implemented - see section 3.7.3 for details).
## Milestone 2: EOBT - 2 hr

### Definition

[M2.definition.1] At EOBT-2 hr most flights will be known in the Airport CDM Platform including if they are regulated or not.
[M2.definition.2] All regulated flights receive a CTOT from Network Operations.
### Origin and priority

[M2.origin_and_priority.1] The CTOT is issued by the Network Operations and is sent to relevant ATS units as well as the departure aerodrome.
[M2.origin_and_priority.2] CTOT flights usually have a priority over unregulated flights.
### Timing

[M2.timing.1] If the flight is regulated, a CTOT is issued at EOBT-2h.
### Data Quality

[M2.data_quality.1] Not applicable.
### Effect

[M2.effect.1] For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.
### Procedures

[M2.procedures.1] To check (before or after take off from outstation) whether AO/GH flight estimates are consistent with the ATC Flight Plan and to inform Network Operations about the updated take off time estimate, using a T-DPI Message.
[M2.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs.
[M2.procedures.3] At EOBT-2 hrs Network Operations is informed through the first T-DPI message.
[M2.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT.
[M2.procedures.5] In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M2.procedures.6] This procedure is triggered by
[M2.procedures.7] - a time stamp, at EOBT - 2h.
### Operational Status (changes to)

[M2.operational_status.1] N. A.
### Action on CDM Operation (ACISP)

[M2.action_on_cdm.1] ETOT/TTOT/CTOT Mark appropriate fields as REGULATED
## Milestone 3: Take Off from Outstation

### Definition

[M3.definition.1] The ATOT from the outstation (ADEP)
### Origin and priority

[M3.origin_and_priority.1] The outstation provides ATOT to the Network Operations and Aircraft Operator.
### Timing

[M3.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M3.data_quality.1] The accuracy of ATOT is +/- 1 minute.
### Effect

[M3.effect.1] If the departure airport is more than 3hrs flying time from the destination airport the ATOT is received from either the Network Operations FUM or via the Aircraft Operator / Ground Handler.
[M3.effect.2] Using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
[M3.effect.3] If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS and send a Flight Update Message (FUM) that provides updates of the flight's progress.
### Procedures

[M3.procedures.1] To check whether the AO/GH estimated landing time after take off from outstation are consistent with the outbound ATC Flight Plan, and when needed inform the Network Operations about the updated take off time estimates using a T-DPI-t Message.
[M3.procedures.2] This check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation.
[M3.procedures.3] A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT.
[M3.procedures.4] Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT.
[M3.procedures.5] In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT.
[M3.procedures.6] In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
[M3.procedures.7] This process is triggered by
[M3.procedures.8] - the take off from outstation.
### Operational Status (changes to)

[M3.operational_status.1] AIRBORNE
### Action on CDM Operation (ACISP)

[M3.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 4: Local Radar Update

### Definition

[M4.definition.1] The flight enters the FIR (Flight Information Region) or the local airspace of the destination airport.
### Origin and priority

[M4.origin_and_priority.1] This information is normally available from the Area Control Centre (ACC) or Approach Control Unit that is associated with an airport.
[M4.origin_and_priority.2] The radar system is able to detect a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
### Timing

[M4.timing.1] Dependent upon the position of the airport in relation to the FIR boundary.
### Data Quality

[M4.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M4.effect.1] Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.
[M4.effect.2] The accuracy of ELDT is particularly important at this stage since downstream decisions are taken, such as stand /gate / aircraft changes, preparation of arrival sequence, preparation of ground handling operations, decisions for connecting passengers.
[M4.effect.3] Uncertainty and ELDT non-accuracy at this stage significantly increase risks for bad and last minute decisions and internal disruptions.
[M4.effect.4] The objective to decrease the number of stand and gate changes in the last 30 minutes requires high accuracy regarding departure and arrival times.
[M4.effect.5] Therefore, taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.
[M4.effect.6] The update of TOBT for the related departing flight takes place following this milestone.
[M4.effect.7] Decisions such as the turn-round period, connecting passengers etc are taken and need to be stable at this event.
[M4.effect.8] An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
### Procedures

[M4.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M4.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M4.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M4.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M4.procedures.5] This process is triggered by
[M4.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M4.operational_status.1] FIR
### Action on CDM Operation (ACISP)

[M4.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 5: Final Approach

### Definition

[M5.definition.1] The flight enters the Final Approach phase at the destination airport.
### Origin and priority

[M5.origin_and_priority.1] This information is normally available from ATC.
[M5.origin_and_priority.2] The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range / position or passes/leaves a predetermined level.
### Timing

[M5.timing.1] Dependent upon local parameters that are defined by ATC.
### Data Quality

[M5.data_quality.1] Must be equal to the accuracy of the ATC system.
### Effect

[M5.effect.1] Update of the ELDT to determine a new TOBT.
[M5.effect.2] When a flight reaches this stage it is usually between 2 and 5 minutes from landing (depending on the parameter set by ATC).
[M5.effect.3] This is often the prompt for many partners to start moving resources connected with the flight, such as positioning a parking marshal and ground handling services.
### Procedures

[M5.procedures.1] To commence the TOBT process and check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M5.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M5.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
[M5.procedures.4] The TTOT tolerance is respected before Network Operations is informed of updated TTOT.
[M5.procedures.5] This process is triggered by
[M5.procedures.6] - the detection of the flight by radar in either FIR, TMA, or on Final Approach.
### Operational Status (changes to)

[M5.operational_status.1] FINAL
### Action on CDM Operation (ACISP)

[M5.action_on_cdm.1] ELDT, EIBT, TOBT and TTOT updated
## Milestone 6: Landed

### Definition

[M6.definition.1] ALDT - Actual Landing Time.
[M6.definition.2] This is the time that an aircraft touches down on a runway.
[M6.definition.3] (Equivalent to ATC ATA - Actual Time of Arrival landing, ACARS=ON).
### Origin and priority

[M6.origin_and_priority.1] Provided by ATC system or by ACARS from equipped aircraft.
### Timing

[M6.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M6.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M6.effect.1] The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator / Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
[M6.effect.2] The EIBT can be updated according to the ALDT +EXIT.
### Procedures

[M6.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M6.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M6.procedures.3] This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan.
[M6.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M6.procedures.5] This process is triggered by
[M6.procedures.6] - Actual Landing Time: ALDT
### Operational Status (changes to)

[M6.operational_status.1] LANDED
### Action on CDM Operation (ACISP)

[M6.action_on_cdm.1] ELDT changes to ALDT, EIBT, TOBT and TTOT updated

## Milestone 9: Final Confirmation of the TOBT

### Definition

[M9.definition.1] The time at which the Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.
### Origin and priority

[M9.origin_and_priority.1] The Aircraft Operator / Ground Handler provides the information.
### Timing

[M9.timing.1] The information is provided t minutes before EOBT (t is a parameter time agreed locally).
### Data Quality

[M9.data_quality.1] Accuracy is agreed locally.
### Effect

[M9.effect.1] The aim of the final TOBT is to give a timely, accurate and reliable assessment of the off-block time.
[M9.effect.2] It is recognised that main benefits of sharing the TOBT are expected in case of disruptions (internal or external).
[M9.effect.3] In such cases, the difference between EOBT (shared by ATC, Network Operations and Stand / Gate Management) and TOBT may be important.
[M9.effect.4] An accurate TOBT at [EOBT-t minutes] is a pre-requisite for ATC to establish a push back / pre-departure sequence.
[M9.effect.5] Emphasis is put on the need for the Aircraft Operator to integrate his own strategy to compute a TOBT related to the flight.
[M9.effect.6] Following the receipt of the TOBT, the ATC system will calculate and provide the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate / stand location, runway in use, and waiting period at the Holding Position, etc. The flight is introduced into the pre-departure sequence.
[M9.effect.7] The Aircraft Operator / Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M9.procedures.1] To check whether the AO/GH TOBT is consistent with the ATC Flight Plan.
[M9.procedures.2] Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
[M9.procedures.3] This check should be performed at a predefined time (local parameter) to confirm TOBT prior to TSAT issue and verify feasibility of the ATC Flight Plan estimates given the updated TOBT.
[M9.procedures.4] A TTOT tolerance is respected before Network Operations is informed on updated TTOT.
[M9.procedures.5] This Milestone Process is actually constantly applicable in the CDM Platform, as soon as a TOBT is available.
[M9.procedures.6] However the confirmed TOBT prior to TSAT has special status, where AO/GH check the quality of TOBT before TSAT issue.
### Operational Status (changes to)

[M9.operational_status.1] IN-BLOCK
### Action on CDM Operation (ACISP)

[M9.action_on_cdm.1] This process is triggered by - a new TOBT or TTOT update.
[M9.action_on_cdm.2] No need to confirm an existing TOBT if it has been manually modified before.

### Definition

[M10.definition.1] The time ATC issues the Target Start Up Approval Time
### Origin and priority

[M10.origin_and_priority.1] ATC
### Timing

[M10.timing.1] The information is provided t-minutes before EOBT, where t is a parameter agreed locally
### Data Quality

[M10.data_quality.1] Accuracy is agreed locally.
### Effect

[M10.effect.1] The flight is stabilised into the pre-departure sequence.
[M10.effect.2] The Aircraft Operator/ Ground Handler, in coordination with the aircrew, can manage the turn-round process accordingly.
### Procedures

[M10.procedures.1] First step: To inform all relevant partners of the TSAT that has been allocated to the flight.
[M10.procedures.2] The Network Operations is informed by a T-DPI-s for non regulated flights.
[M10.procedures.3] Second step: To check whether the number of TOBT updates exceeds a tolerance defined locally, after TSAT has been issued.
[M10.procedures.4] First: The TSAT will indicate to the partners the time when the start up approval can be expected.
[M10.procedures.5] Network Operations will be informed with a T-DPI-s for non regulated flights.
[M10.procedures.6] No check is performed.
[M10.procedures.7] Second: A check shall be performed to see the number of TOBT updates after TSAT has been issued.
[M10.procedures.8] In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.
[M10.procedures.9] This process is triggered by
[M10.procedures.10] - A defined time (local parameter) before TOBT
[M10.procedures.11] - TOBT update after TSAT issue

[M11.definition.2] This is not to be confused with the time passengers are pre-called to the gate via flight information display systems (FIDS) or public address systems.
### Origin and priority

[M11.origin_and_priority.1] Automatic from airport system or manual input by Aircraft Operator/ Ground Handler.
### Timing

[M11.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M11.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M11.effect.1] When boarding commences it gives the Airport CDM Partners a good indication of whether the TOBT/TSAT will be respected.
### Procedures

[M11.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT).
[M11.procedures.2] Second step: To check whether boarding starts in time to respect TOBT and inform the AO/GH in case TOBT needs to be updated.
[M11.procedures.3] Inform of Actual Start Boarding Time (ASBT) when it occurs.
[M11.procedures.4] At a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status.
[M11.procedures.5] This process is triggered by
[M11.procedures.6] - a time variable <value> minutes before TOBT.
### Operational Status (changes to)

## Milestone 12: Aircraft Ready

### Definition

[M12.definition.1] The time when all doors are closed, boarding bridge removed, push back vehicle connected, ready to taxi immediately upon reception of TWR instructions (ARDT).
### Origin and priority

[M12.origin_and_priority.1] Provided by the Aircraft Operator/ Ground Handler.
### Timing

[M12.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M12.data_quality.1] Data is directly available with an accuracy of +/- 1 minute.
### Effect

[M12.effect.1] ATC refines the pre-departure sequence.
[M12.effect.2] The pilot requests start up just before TSAT, following coordination with the Ground Handler.
[M12.effect.3] (Dispatcher / Supervisor / Redcap).
### Procedures

[M12.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up / push-back.
[M12.procedures.2] Second step: To inform the AO/GH that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).
[M12.procedures.3] Inform of ARDT or RDY confirming that the flight follows the indicated TOBT.
[M12.procedures.4] At TOBT + tolerance the AO/GH are informed that TOBT has passed and there has not been a ready status message yet.
[M12.procedures.5] This procedure is triggered by
[M12.procedures.6] - an input to the Airport CDM Platform.

## Milestone 15: Off-Block

### Definition

[M15.definition.1] AOBT - Actual Off-Block Time.
[M15.definition.2] The time the aircraft pushes back/vacates the parking position (Equivalent to Airline/Handler ATD - Actual Time of Departure ACARS=OUT).
### Origin and priority

[M15.origin_and_priority.1] ACARS equipped aircraft or automated docking systems or ATC systems (e.g. A-SMGCS) or by manual input.
### Timing

[M15.timing.1] The information is directly available after occurrence of the milestone.
### Data Quality

[M15.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M15.effect.1] TTOT updated considering the EXOT.
### Procedures

[M15.procedures.1] First step: To inform all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back / taxi from parking position.
[M15.procedures.2] Second step: To check if TTOT changes by more than the agreed tolerance and inform Network Operations.
[M15.procedures.3] Inform of AOBT when it occurs.
[M15.procedures.4] AOBT always triggers an A-DPI message to Network Operations or in the case of remote holding at a defined time prior to TTOT.
[M15.procedures.5] After a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.
[M15.procedures.6] This process is triggered by AOBT detection.
### Operational Status (changes to)

[M15.operational_status.1] OFF-BLOCK
### Action on CDM Operation (ACISP)

[M15.action_on_cdm.1] AOBT recorded
## Milestone 16: Take Off

### Definition

[M16.definition.1] ATOT - Actual Take Off Time.
[M16.definition.2] This is the time that an aircraft takes off from the runway.
[M16.definition.3] (Equivalent to ATC ATD-Actual Time of Departure, ACARS = OFF).
### Origin and priority

[M16.origin_and_priority.1] Provided by ATC system or from ACARS equipped aircraft.
### Timing

[M16.timing.1] The information is directly available as soon as possible after occurrence of the milestone.
### Data Quality

[M16.data_quality.1] Data is available with an accuracy of +/- 1 minute.
### Effect

[M16.effect.1] FSA and MVT messages are sent.
### Procedures

[M16.procedures.1] To inform all relevant Airport CDM Partners about the actual take off.
[M16.procedures.2] An airborne message is generated and the flight is removed from the departure sequence.
[M16.procedures.3] This process is triggered by Tower FDPS, A-SMGCS / Radar detection or ACARS.
### Operational Status (changes to)

[M16.operational_status.1] DEPARTED / TAKE OFF
### Action on CDM Operation (ACISP)

[M16.action_on_cdm.1] ATOT recorded

# The model

class AirportCdmPartner (package Stakeholders): A generalization of any party participating in the Airport CDM process that originates or receives flight information and is informed by milestone procedures.

class AircraftOperator (package Stakeholders): The airline or operator that submits the ATC Flight Plan, provides TOBT and turn-round estimates, and manages the aircraft's turn-round.
  operation provideFinalTobt(flight: Flight): OffBlockTime; The Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.

class GroundHandler (package Stakeholders): The party that performs ground handling operations and, with the Aircraft Operator, provides turn-round times such as TOBT, ACGT and ARDT.
  operation provideFinalTobt(flight: Flight): OffBlockTime; The Aircraft Operator or Ground Handler provide their most accurate TOBT taking into account the operational situation.

class AirTrafficControl (package Stakeholders): The air traffic control units (Area Control Centre, Approach Control, Tower) that manage flight plans, sequencing and start-up approvals.
  operation issueTsat(flight: Flight): StartUpApprovalTime; ATC issues the Target Start Up Approval Time t-minutes before EOBT, where t is a parameter agreed locally.

class NetworkOperations (package Stakeholders): The network management function that issues CTOT, monitors flight progress via ETFMS, and is informed of updated estimates through DPI messages.
  operation issueCtot(flight: Flight): TakeOffTime; If the flight is regulated, a CTOT is issued by Network Operations at EOBT-2h.

class FlightCrew (package Stakeholders): The pilot and aircrew who request and receive start-up approval and coordinate readiness with the Ground Handler.

class StandGateManagement (package Stakeholders): The stakeholder responsible for stand and gate allocation decisions that depend on accurate ELDT and EOBT sharing.

class Outstation (package Stakeholders): The departure aerodrome of the outbound flight when different from the airport of interest, which provides ATOT to Network Operations and the Aircraft Operator.
  operation provideAtot(flight: Flight): TakeOffTime; The outstation provides ATOT to the Network Operations and Aircraft Operator.

class Flight (package Flights): A single scheduled arriving or departing movement of an aircraft, carrying its operational status and the time quantities that describe its progress.
  attribute operationalStatus: FlightOperationalStatus; The current operational status of the flight, updated at each milestone (e.g. INITIATED, AIRBORNE, LANDED, OFF-BLOCK).
  attribute isRegulated: Boolean; Whether the flight is regulated and has received a CTOT from Network Operations at EOBT-2 hours; appropriate fields are marked as REGULATED.
  operation updateOperationalStatus(newStatus: FlightOperationalStatus): void; The flight's operational status changes to the status recorded at each milestone (e.g. INITIATED, AIRBORNE, FIR, FINAL, LANDED, IN-BLOCK, SEQUENCED, BOARDING, READY, OFF-BLOCK, DEPARTED/TAKE OFF).

class TurnRound (package Flights): The linked pair of an arriving and a departing flight of the same aircraft at an airport, over which the turn-round period is defined and analysed.
  attribute minimumTurnRoundTime: DurationEstimate; The defined minimum turn-round period (MTTT) used as a calculation basis for TOBT and TTOT.
  attribute estimatedTurnRoundTime: DurationEstimate; The estimated turn-round period (ETTT) used to calculate TOBT after ground handling starts.

class Aircraft (package Flights): The physical aircraft performing a flight, identified by type and registration, which may be updated from the ATC Flight Plan.
  attribute aircraftType: String; The type of aircraft performing the flight, which may be updated from the ATC Flight Plan.
  attribute registration: String; The aircraft registration provided as part of consistent flight data before the first E-DPI message.

class AtcFlightPlan (package Flights): The ICAO flight plan, including repetitive flight plans, submitted by the Aircraft Operator and distributed by the IFPS to ATC units.
  attribute isRepetitive: Boolean; Whether the flight plan is a repetitive flight plan (RFPL) covering daily or weekly flights.
  attribute firstDestination: String; The first destination aerodrome data that must be consistent before the first E-DPI message is sent.

class AirportSlot (package Flights): The airport slot allocated under the airport slot programme against which the ATC Flight Plan and flight data are checked for consistency.
  attribute allocatedTime: DateTime; The time allocated to the flight under the airport slot programme, which the ATC Flight Plan must be consistent with.
  attribute coordinationStatus: AirportCoordinationStatus; Whether the airport is coordinated or non coordinated, which determines whether the outbound flight is already known or must be initiated from the flight plan.

class AirportFlightData (package Flights): The locally held airport data describing a flight that must be consistent with the ATC Flight Plan and Airport Slot before the first E-DPI is sent.

class TimeQuantity (package Timings): An abstract time value describing a flight's progress, recorded with its prefix, originator and time of update, with every successive value kept rather than overwritten.
  attribute value: DateTime; The time value of this quantity for the flight.
  attribute prefix: TimePrefix; Identifies whether the value is scheduled, estimated, target, actual, or calculated.
  attribute originator: String; The stakeholder or system that provided or calculated this value.
  attribute recordedAt: DateTime; The time this value was recorded; every successive value is appended rather than overwriting the prior one, so the turn-round can be analysed afterwards.
  operation recordUpdate(newValue: DateTime, originator: String, recordedAt: DateTime): void; Every successive value is kept, with its originator and time of update, so a turn-round can be analysed afterwards; an update appends rather than overwriting.

class OffBlockTime (package Timings): The scheduled, target or actual value of the off-block event (EOBT, TOBT, AOBT) for a flight.
  attribute accuracy: Duration; The accuracy of the actual off-block time (AOBT), +/- 1 minute.

class InBlockTime (package Timings): The estimated or actual value of the in-block event (EIBT, AIBT) for an arriving flight.
  attribute accuracy: Duration; The accuracy of the actual in-block time (AIBT), +/- 1 minute.

class LandingTime (package Timings): The estimated or actual value of the landing event (ELDT, ALDT) for an arriving flight.
  attribute accuracy: Duration; The accuracy of the actual landing time (ALDT), +/- 1 minute.

class TakeOffTime (package Timings): The estimated, target, calculated or actual value of the take-off event (ETOT, TTOT, CTOT, ATOT) for a departing flight.
  attribute accuracy: Duration; The accuracy of the actual take-off time (ATOT), +/- 1 minute.
  attribute tolerance: Duration; The TTOT tolerance (e.g. 5 minutes after take off from outstation) respected before Network Operations is informed of an updated TTOT.

class StartUpApprovalTime (package Timings): The target or actual value of the start-up approval event (TSAT, ASAT) for a departing flight.
  attribute toleranceWindow: Duration; The locally agreed TSAT tolerance window within which start-up must be requested and approved before partners are alerted.

class StartBoardingTime (package Timings): The actual time at which boarding of a flight starts (ASBT).
  attribute accuracy: Duration; The accuracy of the actual start boarding time (ASBT), +/- 1 minute.

class ReadyTime (package Timings): The actual time at which an aircraft is ready for start-up and push-back (ARDT).
  attribute accuracy: Duration; The accuracy of the actual ready time (ARDT), +/- 1 minute.
  attribute tolerance: Duration; The tolerance after TOBT at which the AO/GH is informed that no ready status has yet been received.

class StartUpRequestTime (package Timings): The actual time at which start-up is requested by the flight crew (ASRT).
  attribute accuracy: Duration; The accuracy of the actual start-up request time (ASRT), +/- 1 minute.

class DurationEstimate (package Timings): A duration used to calculate other time quantities, such as estimated taxi-out time (EXOT), estimated taxi-in time (EXIT), minimum turn-round time (MTTT), estimated turn-round time (ETTT), or the flight plan's estimated elapsed time.
  attribute value: Duration; The value of the estimated duration.
  attribute kind: DurationKind; Identifies which duration estimate this is: estimated taxi-out time (EXOT), estimated taxi-in time (EXIT), minimum turn-round time (MTTT), estimated turn-round time (ETTT), or estimated elapsed time.

class Milestone (package Milestones): An abstract representation of one of the sixteen defined events in the CDM process, each with its own trigger, timing rule, effect and procedure.
  attribute milestoneNumber: Integer; The sequential number, from 1 to 16, identifying this milestone in the CDM process.
  attribute resultingStatus: FlightOperationalStatus; The operational status the flight changes to when this milestone occurs.

class AtcFlightPlanActivation (package Milestones): The milestone at which the ATC Flight Plan is submitted and the Airport CDM Platform is initiated for the flight.
  operation checkConsistency(atcFlightPlan: AtcFlightPlan, airportSlot: AirportSlot, airportFlightData: AirportFlightData): Boolean; This check shall be performed to verify the consistency between the ATC Flight Plan, Airport Slot and Airport flight data before the first E-DPI is sent.
  operation validateDataBeforeFirstEdpi(sobt: OffBlockTime, aircraftRegistration: String, firstDestination: String): Boolean; The AO must provide correct information before this first E-DPI message, in order to feed Network Operations with consistent SOBT, aircraft registration, and first destination data, as early in time as possible. The E-DPI message should not be sent if no or inconsistent information is provided.
  operation initiateOutboundFlight(flightPlan: AtcFlightPlan): Flight; For non coordinated airports, the flight plan is used to initiate the outbound flight.
  operation checkFlightReadiness(actualReadyTime: DateTime, eobt: OffBlockTime): Boolean; The flight is ready not later than 15 minutes after the planned EOBT.

class EobtMinusTwoHourCheck (package Milestones): The milestone at EOBT-2 hours at which regulated flights receive a CTOT and Network Operations is informed by the first T-DPI message.
  operation checkFeasibility(flightEstimates: TakeOffTime, atcFlightPlan: AtcFlightPlan): Boolean; This check shall be performed to verify feasibility of the ATC Flight Plan estimated off block time at EOBT-2 hrs, by checking whether AO/GH flight estimates are consistent with the ATC Flight Plan.
  operation informNetworkOperationsViaFirstTdpi(flight: Flight): void; At EOBT-2 hrs Network Operations is informed through the first T-DPI message about the updated take off time estimate.
  operation calculateTtot(eibt: InBlockTime, mttt: DurationEstimate, exot: DurationEstimate, eobt: OffBlockTime, tobt: OffBlockTime): DateTime; Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT, if later than EOBT+EXOT. In the case of manual input of TOBT, this estimate will override the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
  operation updateEldtFromFum(fumMessage: FlightUpdateMessage): DateTime; For inbound flights, ELDT is updated based on information provided by the FUM messages, taking into account the actual progress of the flight.
  operation markFieldsAsRegulated(flight: Flight): void; Mark appropriate fields as REGULATED.

class TakeOffFromOutstation (package Milestones): The milestone at which ATOT from the outstation is received and used to update ELDT and, when needed, inform Network Operations via a T-DPI-t message.
  operation calculateEldtFromAtot(atot: TakeOffTime, estimatedElapsedTime: DurationEstimate): DateTime; If the departure airport is more than 3hrs flying time from the destination airport, using the ATOT an ELDT can be calculated by using the Estimated Elapsed Time on the FPL.
  operation checkFeasibility(estimatedLandingTime: LandingTime, atcFlightPlan: AtcFlightPlan): Boolean; This check shall be performed to verify feasibility of the ATC Flight Plan at take off from outstation, by checking whether the AO/GH estimated landing time is consistent with the outbound ATC Flight Plan.
  operation calculateTtot(eibt: InBlockTime, mttt: DurationEstimate, exot: DurationEstimate, eobt: OffBlockTime, tobt: OffBlockTime): DateTime; Calculation basis for the TTOT shall take into account EIBT+MTTT+EXOT. In case EOBT is later than EIBT+MTTT, TTOT equals EOBT+EXOT. In the case where TOBT is available this prediction will overrule the EIBT+MTTT estimate, hence TTOT equals TOBT+EXOT.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; A TTOT tolerance of 5 minutes is respected before Network Operations is informed of the updated TTOT using a T-DPI-t Message.

class LocalRadarUpdate (package Milestones): The milestone at which the flight is detected entering the FIR or local airspace, triggering a TOBT process and ELDT/EIBT update.
  operation triggerTobtUpdate(eldt: LandingTime): void; Update of the ELDT can trigger a new TOBT to be entered by the AO/GH, or calculated automatically by the Airport CDM Platform.
  operation checkStandGateChangePreference(eldt: LandingTime, exit: DurationEstimate): Boolean; Taking into account the taxi-in time (EXIT), any change to a stand or gate is not preferred after ELDT-30'.
  operation calculateEibt(eldt: LandingTime, exit: DurationEstimate): DateTime; An estimated in-block time (EIBT) is computed using the ELDT and the estimated taxi-in time.
  operation checkFeasibility(tobt: OffBlockTime, atcFlightPlan: AtcFlightPlan): Boolean; This process commences the TOBT process and checks whether the AO/GH TOBT is consistent with the ATC Flight Plan; this check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class FinalApproach (package Milestones): The milestone at which the flight enters final approach at the destination, triggering a new TOBT determination.
  operation triggerTobtUpdate(eldt: LandingTime): void; Update of the ELDT to determine a new TOBT.
  operation checkFeasibility(tobt: OffBlockTime, atcFlightPlan: AtcFlightPlan): Boolean; This process commences the TOBT process and checks whether the AO/GH TOBT is consistent with the ATC Flight Plan; this check shall be performed to verify feasibility of the ATC Flight Plan given the up-dated TOBT.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class Landed (package Milestones): The milestone at which ALDT is recorded, triggering updates to TOBT, TTOT and EIBT.
  operation updateTobtAndTtot(aldt: LandingTime, turnRoundPeriod: DurationEstimate): void; The occurrence of ALDT triggers an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator/Ground Handler, calculated on the basis of the defined turn-round period for the departing flight.
  operation calculateEibt(aldt: LandingTime, exit: DurationEstimate): DateTime; The EIBT can be updated according to the ALDT+EXIT.
  operation checkFeasibility(tobt: OffBlockTime, atcFlightPlan: AtcFlightPlan): Boolean; This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan, by checking whether the AO/GH TOBT is consistent with the ATC Flight Plan.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class InBlock (package Milestones): The milestone at which AIBT is recorded, triggering updates to TOBT and TTOT based on the estimated turn-round period.
  operation updateTobtAndTtot(aibt: InBlockTime, turnRoundPeriod: DurationEstimate): void; The occurrence of AIBT should trigger an update of downstream estimates: TOBT and TTOT are updated automatically or inserted manually by the Aircraft Operator/Ground Handler, calculated on the basis of the estimated turn-round period for the departing flight.
  operation checkFeasibility(tobt: OffBlockTime, atcFlightPlan: AtcFlightPlan): Boolean; This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan, by checking whether the AO/GH TOBT is consistent with the ATC Flight Plan.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class GroundHandlingStarted (package Milestones): The milestone at which ground handling commences (ACGT) for first-of-day or long-parked flights, triggering a TOBT update.
  operation updateTobt(acgt: DateTime, turnRoundPeriod: DurationEstimate): void; The occurrence of ACGT triggers an update of downstream estimates: TOBT is updated automatically or inserted manually by the Aircraft Operator/Ground Handler, calculated on the basis of the estimated turn-round period for the departing flight.
  operation checkFeasibility(tobt: OffBlockTime, atcFlightPlan: AtcFlightPlan): Boolean; This check shall be performed to verify feasibility of the ATC Flight Plan given the updated TOBT or ATC Flight Plan, by checking whether the AO/GH TOBT is consistent with the ATC Flight Plan.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.

class FinalConfirmationOfTobt (package Milestones): The milestone at which the Aircraft Operator or Ground Handler provides their most accurate TOBT ahead of TSAT issue.
  operation checkFeasibility(tobt: OffBlockTime, atcFlightPlan: AtcFlightPlan): Boolean; This check should be performed at a predefined time (local parameter) to confirm TOBT prior to TSAT issue and verify feasibility of the ATC Flight Plan estimates given the updated TOBT, by checking whether the AO/GH TOBT is consistent with the ATC Flight Plan.
  operation notifyNetworkOperationsIfToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): void; Network Operations is informed when the TTOT changes by more than the agreed TTOT tolerance.
  operation introduceIntoPredepartureSequence(flight: Flight): void; The flight is introduced into the pre-departure sequence.
  operation requiresConfirmation(tobt: OffBlockTime, manuallyModified: Boolean): Boolean; No need to confirm an existing TOBT if it has been manually modified before.

class TsatIssued (package Milestones): The milestone at which ATC issues the Target Start-Up Approval Time and checks the number of subsequent TOBT updates.
  operation notifyPartnersOfTsat(tsat: StartUpApprovalTime): void; To inform all relevant partners of the TSAT that has been allocated to the flight.
  operation informNetworkOperationsViaTdpiS(flight: Flight): void; The Network Operations is informed by a T-DPI-s for non regulated flights.
  operation checkTobtUpdateCountExceedsTolerance(tobtUpdateCount: Integer, threshold: Integer): Boolean; A check shall be performed to see the number of TOBT updates after TSAT has been issued. In case the number of TOBT updates exceeds a threshold, then the TOBT input should be processed according to local procedure.

class BoardingStarts (package Milestones): The milestone at which boarding of passengers physically starts, used to check whether TOBT will be respected.
  operation notifyActualStartBoardingTime(asbt: StartBoardingTime): void; To inform all relevant Airport CDM Partners of Actual Start Boarding Time (ASBT) when it occurs.
  operation checkBoardingStatus(asbt: StartBoardingTime, tobt: OffBlockTime): Boolean; At a certain time before TOBT (local variable e.g. corresponding to aircraft type) a check shall be performed to check the boarding status, whether boarding starts in time to respect TOBT, and inform the AO/GH in case TOBT needs to be updated.

class AircraftReady (package Milestones): The milestone at which the aircraft is ready for start-up and push-back, informing partners and checking against TOBT.
  operation notifyActualReadyTime(ardt: ReadyTime): void; To inform all relevant Airport CDM Partners of Actual Ready Time (ARDT) in the Airport CDM Platform and that the aircraft is ready for start up / push-back.
  operation checkReadyStatusReceived(tobt: OffBlockTime, tolerance: Duration): Boolean; At TOBT + tolerance the AO/GH are informed that TOBT has passed and the Airport CDM Platform has not yet received ARDT or Ready Status (RDY).

class StartUpRequested (package Milestones): The milestone at which start-up is requested by the pilot, with an alert if no request is made within the TSAT tolerance window.
  operation notifyActualStartUpRequestTime(asrt: StartUpRequestTime): void; To inform all relevant Airport CDM Partners of Actual Start up Request Time (ASRT) in the Airport CDM Platform.
  operation checkStartUpRequestedWithinTolerance(tsat: StartUpApprovalTime, tolerance: Duration): Boolean; To alert all relevant Airport CDM Partners when no start up has been requested inside the locally agreed TSAT tolerance window. If the start up request is not made by TSAT + tolerance, the AO/GH is informed that no start up has been requested, and should update TOBT.

class StartUpApproved (package Milestones): The milestone at which ATC grants start-up approval, checked against TSAT with resequencing if not granted in time.
  operation notifyActualStartUpApprovalTime(asat: DateTime): void; To inform all relevant Airport CDM Partners of Actual start up approval Time (ASAT) in the Airport CDM Platform and that the aircraft has received start up approval / push-back clearance.
  operation checkAsatAgainstTsat(asat: DateTime, tsat: StartUpApprovalTime, tolerance: Duration): Boolean; A check shall be performed to check if ASAT is in accordance to TSAT and to alert all relevant Airport CDM Partners when no start up has been granted. In case the start up approval is not granted at TSAT + tolerance, all relevant partners should be informed.
  operation resequenceFlight(flight: Flight): void; The flight will be re-sequenced.

class OffBlock (package Milestones): The milestone at which the aircraft pushes back, recorded as AOBT and always triggering an A-DPI message to Network Operations.
  operation notifyActualOffBlockTime(aobt: OffBlockTime): void; To inform all relevant Airport CDM Partners of Actual Off-Block Time (AOBT) in the Airport CDM Platform and that the aircraft has commenced push-back / taxi from parking position.
  operation updateTtot(aobt: OffBlockTime, exot: DurationEstimate): DateTime; TTOT updated considering the EXOT.
  operation checkTtotToleranceExceeded(newTtot: TakeOffTime, oldTtot: TakeOffTime): Boolean; To check if TTOT changes by more than the agreed tolerance and inform Network Operations.
  operation sendADpi(flight: Flight): void; AOBT always triggers an A-DPI message to Network Operations or in the case of remote holding at a defined time prior to TTOT. After a first A-DPI is sent this check shall be performed to check TTOT updates against the TTOT tolerance before Network Operations is informed, with a new A-DPI, of the updated TTOT.

class TakeOff (package Milestones): The milestone at which the aircraft takes off, recorded as ATOT, generating an airborne message and removing the flight from the departure sequence.
  operation notifyActualTakeOff(atot: TakeOffTime): void; To inform all relevant Airport CDM Partners about the actual take off.
  operation generateAirborneMessage(flight: Flight): void; An airborne message is generated and the flight is removed from the departure sequence.
  operation sendFsaAndMvtMessages(flight: Flight): void; FSA and MVT messages are sent.

class AirportCdmPlatform (package Systems): The central CDM system that is initiated for each flight, processes available information, and performs the Action on CDM Operation updates and partner notifications described at each milestone.
  operation commenceDpiProcess(flight: Flight): void; The DPI process commences the correct messaging with Network Operations (if implemented).

class AtcSystem (package Systems): The ATC system, including Tower FDPS, that provides landing, in-block and off-block times and calculates EXOT.
  operation calculateExot(trafficLoad: String, gateStandLocation: String, runwayInUse: String, holdingPositionWaitPeriod: Duration): DurationEstimate; Following the receipt of the TOBT, the ATC system will calculate and provide the Estimated Taxi-Out Time (EXOT) based on the predicted traffic load, gate/stand location, runway in use, and waiting period at the Holding Position, etc.

class SurveillanceRadarSystem (package Systems): The radar system (including A-SMGCS) that detects a flight by its assigned SSR code when it crosses the FIR/ATC boundary or enters final approach.
  operation detectFlightAtFirBoundary(ssrCode: String): void; The radar system is able to detect a flight based upon the assigned SSR code when the flight crosses a defined FIR/ATC boundary.
  operation detectFlightOnFinalApproach(ssrCode: String): void; The radar system detects a flight based upon the assigned SSR code and identifies when the flight crosses either a defined range/position or passes/leaves a predetermined level.

class Acars (package Systems): The aircraft communications addressing and reporting system that provides landing, in-block, off-block and take-off times for equipped aircraft.

class AutomatedDockingSystem (package Systems): An automated system that detects an aircraft's arrival in-block or departure off-block.

class Etfms (package Systems): The Network Operations system that monitors a flight's progress and generates Flight Update Messages when the flight is within three hours of the destination.
  operation monitorFlightProgress(flight: Flight): void; If the flight is within 3hrs flying time of the destination airport the Network Operations monitors progress of the flight using the ETFMS.
  operation sendFum(flight: Flight): FlightUpdateMessage; Network Operations sends a Flight Update Message (FUM) that provides updates of the flight's progress.

class Ifps (package Systems): The system that distributes the submitted ATC Flight Plan to all involved ATC units.

class FlightInformationDisplaySystem (package Systems): The airport system, including flight information display and public address systems, used to inform partners and pre-call passengers.

class DpiMessage (package Messages): A Departure Planning Information message exchanged with Network Operations at defined milestones, distinguished by its type (E-DPI, T-DPI, T-DPI-t, T-DPI-s, A-DPI).
  attribute messageType: DpiMessageType; The type of DPI message exchanged with Network Operations (E-DPI, T-DPI, T-DPI-t, T-DPI-s, or A-DPI).
  attribute sobt: OffBlockTime; The scheduled off-block time carried in the first E-DPI message, required to be consistent before it is sent.
  attribute aircraftRegistration: String; The aircraft registration carried in the first E-DPI message.
  attribute firstDestination: String; The first destination data carried in the first E-DPI message.

class FlightUpdateMessage (package Messages): The FUM message sent by Network Operations that provides updates of an inbound flight's progress.

class ReadyStatusMessage (package Messages): The Ready Status (RDY) message confirming that a flight follows the indicated TOBT and is ready for start-up.

class StartUpRequestMessage (package Messages): The message by which the flight crew requests start-up, made by voice or DCL.
  attribute method: StartUpRequestMethod; The method by which the start-up request is made, by voice or by DCL.

class MovementMessage (package Messages): A message sent on actual take-off informing partners of the flight's movement, including FSA, MVT and the airborne message.
  attribute messageType: MovementMessageType; The type of movement message sent on actual take off (FSA, MVT, or airborne message).
